## Prochaine étape

➡️ **Session 40 : prompt P2, chapitre 20 (Deep learning et premiers pas en PyTorch), 1ʳᵉ partie** (`docs/syllabus/data/ch20.json`, dossier `chapitres/ch20_deep_learning`, deux sessions de génération) ; pièce jointe : le **Volume 2** du livre (ch. 20, p. 872-926). Toujours valable (checkpoints I à III, ch. 7 à 16, audit P5) :

- les modules « à la scikit-learn » (`fit`/`predict`, attributs appris suffixés par `_`) : les énoncés disent ce que `fit` apprend et ce qui est lu à chaque appel ; une cellule de vérification n'enchaîne jamais `.fit(...)` sur un objet de l'apprenant (helper `fitted` du ch. 7 : un `fit` sans `return self` est signalé par les tests, pas par une erreur de la cellule) ; un `fit` peut poser des attributs privés (`_nom`), que `clone` ignore ;
- une cellule de vérification survit à une fonction qui renvoie `None` (helper `returned` : « as-tu oublié le return ? »), à une liste ou un tableau au lieu d'un tuple, à un résultat de mauvaise forme (un message dit la forme attendue), à une cellule réexécutée et à un noyau redémarré ; ses messages ne parlent pas d'un outil que le contexte exclut ;
- une valeur calculée dans une cellule TODO se vérifie **sans** `computed=True` (l'introduction de la partie dit de ne pas arrondir) ; `computed=True` reste pour les valeurs calculées par une fonction de l'apprenant dans la cellule de vérification ;
- les messages `mistakes` d'une réponse lue sur une figure ou dans un tableau ne disent ni « avant » ni « après », ni quel élément ajouter ou retirer ; une question « dans tes notes » d'un 🔮 ne suppose pas la réponse ; un 🔮 fait prédire ce que la fiche ne dit pas déjà (au ch. 9, des détails chiffrés) ;
- les chiffres d'une cellule d'observations, des indices et des solutions sont relus contre les sorties exécutées ;
- une cellule de vérification qui appelle le code d'un autre exercice le déclare dans `prereq` et ce prérequis est dans les mêmes parcours (`syllabus.py check` le vérifie) ; si ce code manque ou suit mal sa docstring, la cellule le dit en renvoyant à l'exercice (⏳ ou ❌), puis continue ;
- la fiche ne suit pas le livre phrase à phrase : un algorithme décrit par le livre devient du pseudo-code ou un exemple à nous, un exemple du livre est résumé en une ou deux phrases avec ses pages (BIBLE §3) ; les encadrés « Le livre : » des 🕰️ résument fidèlement ce qu'il dit ;
- les exemples de format ne valent jamais une réponse du chapitre ; plusieurs lettres sont acceptées dans le désordre, séparées, entre parenthèses ou avec « et » entre elles (`wb.check`, sessions 18 et 19) ; une réponse « liste d'entiers » dont une erreur classique n'est pas entière s'enregistre avec `decimals=1` (sinon le conseil d'arrondir passe avant l'erreur classique) ;
- les tests d'un module passent des **copies** des tableaux à la fonction de l'apprenant (sauf les tests `..._does_not_modify_...`), et la première ligne de chaque message porte l'indice utile ;
- les vérificateurs simulés travaillent dans une copie faite avec `tar` (`rsync` n'est pas installé), avec des commandes enchaînées par `&&` ; après chaque vérificateur, `git status mon_travail` doit être propre.
- une valeur proche d'une limite d'arrondi s'enregistre avec un autre nombre de décimales (`record` le signale ; 9.18 c est à 5 décimales) ;
- les questions « dans tes notes » d'un 🔮 qui supposent le résultat vont dans une cellule markdown placée **après** l'expérience (`after=[("code", guarded(...)), ("md", ...)]`, comme 9.13 et 9.19) ;
- une variante chiffrée des solutions donne son protocole (graines, grilles, `max_iter`) ; une phrase générale (« tous les poids rétrécissent », « la dernière baisse ») se vérifie sur les sorties ; une mesure à queue lourde (la variance d'une famille presque sans pénalité) se donne avec sa dispersion d'une graine à l'autre ;
- une classe fournie qui appelle le code de l'apprenant (comme `PolyRidge`) traduit ses `NotImplementedError` en messages français qui renvoient à l'exercice ; une vérification d'un modèle linéaire compare aussi l'ordonnée à l'origine.
- un 🔮 dont la réponse dépend d'une graine est refait (10.17 c) ; la cellule « dans tes notes » placée après une expérience 🔮 est visible avant l'exécution : ses questions restent neutres ; les noms des tests sont visibles (`pytest -q` liste les échecs dès le stub) : aucun ne donne la réponse d'un 🔮 ; la fiche, les flashcards, le formulaire et les erreurs fréquentes non plus ;
- une affirmation « séparable », « pas séparable » ou « n'a pas convergé » se vérifie (programme linéaire `scipy.optimize.linprog`, nombre d'époques réel), jamais d'après l'allure d'une courbe ;
- un 🐛 à plusieurs bugs se vérifie par des diagnostics enchaînés, un par bug, dans l'ordre où ils se masquent (10.22) ; une expérience longue qui appelle le code de l'apprenant commence par un petit contrôle (arrêt, valeur sur un jeu choisi pour distinguer les erreurs courantes) et ne se lance que s'il passe (10.23) ; un test révélé « une fois par session » fige aussi ses autres mesures à la première révélation (10.25) ;
- un mutant de la référence par erreur classique (comparateur, labels, biais, arrêt, mélange, types) : les tests doivent tous les attraper, sauf ceux qu'on accepte explicitement (session 21 : 31 sur 32, `score` en `np.float64` accepté).
- dans une cellule TODO qui définit plusieurs fonctions, chaque stub nomme la sienne (`raise NotImplementedError("family_counts_14")`) : la ligne ⏳ dit laquelle manque ; une réponse tapée se vérifie dans son propre bloc `wb.attempt` (ou avant tout appel de fonction), pour qu'une fonction pas encore écrite ne la cache pas (11.17, 11.27) ;
- dans une suite de codes (« IDIIDD »), le message d'une erreur classique désigne l'élément fautif et la notion à relire, jamais la bonne catégorie ; pour un choix multiple, il ne nomme pas l'élément en trop ou manquant ; deux réponses qui ne diffèrent qu'à la dernière décimale demandée (avec et sans remise) se demandent avec une décimale de plus ;
- un mini-exemple de la fiche ne reprend ni les nombres ni le cas d'un exercice papier (ch. 11 : 16 bits et les carrés des entiers, au lieu de 8 bits et des décimales de π) ; un quiz qui doit tester le transfert ne reprend pas mot pour mot un exemple de la fiche ;
- une numérotation (bras, classes, indices) est la même dans la fiche, les figures et les exercices : à partir de 0 comme en Python ;
- un test d'infrastructure qui charge une autre implémentation (`wb.load_mylearn("ref")`) ne doit pas fausser les tests suivants : `mylearn_module` remet l'implémentation de la session avant chaque import (session 22) ; un contrôle par mutation sépare les mutants équivalents (à documenter) des vrais trous (un test de plus).
- après toute reconstruction par son script, un notebook de solutions est réexécuté, puis `build_answers.py` relancé (un notebook réécrit sans sorties casse `answers.json`) ;
- une exigence qui ne se lit pas dans la valeur (une standardisation sur toutes les lignes ne change la RMSE qu'à la 5ᵉ décimale) se vérifie sur ce que reçoit une fonction fournie : une enveloppe aux mêmes noms de paramètres, restaurée dans un `finally` (CP2.10) ; le seuil d'un message (« trop près », « nettement plus bas ») sépare les causes, et un symptôme à plusieurs causes possibles les nomme toutes (MP2.5) ;
- une action irréversible d'un notebook (ouvrir le coffre du test, écrire un fichier gelé) passe par une porte : les garde-fous en échec sont mémorisés par cellule (`checks_of`), la décision se compare sous une forme normalisée (`canonical`), et le message dit ce qui bloque (MP2.6) ;
- une validation croisée de l'apprenant se vérifie fold par fold contre la même chaîne apprise par scikit-learn dans chaque fold, pas seulement par un score voisin ; les tests d'un projet ne tirent jamais de données dans le jeu de test gelé ; une copie qui protège des données partagées (les folds) ne dispense pas de vérifier que la fonction les laisse intactes (MP2.5 compare les copies après l'appel, un test `..._do_not_modify_...` fait de même).
- le vocabulaire du §5 vaut partout, titres publiés et messages compris : `tests/infra/test_terminology.py` refuse « époque », « lot », « étiquette », « perte »… ; une glose s'écrit en italique après une parenthèse, un sens courant se déclare dans `FORBIDDEN` (session 24) ;
- une mesure de temps ne s'enregistre jamais comme réponse (un `verdict` à seuil) ; `build_answers.py` refuse une bonne réponse dont l'empreinte change, et `--accept-answer-changes` ne se passe qu'après avoir vérifié chaque réponse listée ;
- aucun ⚠️ « proche d'une limite d'arrondi » ne reste dans un corrigé : on change le nombre de décimales en essayant plusieurs valeurs (avec 26 éléments, une limite tombe souvent près de l'un d'eux) ;
- les titres du contrat (JSON) sont ceux que publient 02, 04, 05 et les notebooks ; les rappels y sont titrés sans préfixe (« Ch. N : » est ajouté à la publication, `syllabus.py check` le vérifie, comme le champ `check` d'un exercice qui a des réponses) ;
- encadrés : sujet dans le gras (« **Rappel maths — sujet** », « **Le livre, corrigé — sujet** »…), tableau des pièges `| Piège | Exemple | Ce qu'il faut faire |` (§14) ; $p$ features, $n$ exemples (§6) ;
- un notebook ne suppose pas PyTorch avant le ch. 20 (import dans un `try`, ⏳ « sur Colab ») ; un test d'oracle PyTorch se marque `needs_torch` ;
- le modèle du tableau de bord ne contient que les chapitres publiés (`syllabus.py build`) : une section apparaît quand le chapitre est fini (sans `EN_COURS.md`).
- à partir de la partie III, l'énoncé d'un 🔨/📦 donne le **contrat** (signature, entrées et sorties, conventions et erreurs que vérifient les tests) ; la **méthode** passe dans les indices 1 et 2, et la cellule TODO ne garde que la signature et la docstring (§12, point 8) ;
- l'indice 3 d'une réponse courte résout le **premier** item, puis donne le critère ou le calcul posé, jamais le verdict, la lettre ni la valeur ; celui d'un exercice de code donne la signature, le squelette et deux ou trois lignes clés, jamais la fonction complète ; un indice de 🔮 ne révèle pas l'issue ; une solution ne renvoie jamais au code d'un indice (§12) ;
- dans `05_solutions.md`, chaque exercice a sa démarche, ses erreurs fréquentes et une variante **avec sa réponse** (nombres recalculés) ; « À retenir » ne remplace les deux dernières que pour un item court de la partie 0 ; une variante n'anticipe ni un exercice suivant ni un chapitre ultérieur ; une rubrique qui suit une liste numérotée est précédée d'une ligne vide (sinon elle s'affiche dans le dernier item) ;
- nouveaux modules `mylearn` : une entrée avec NaN est refusée (`ValueError` « … remove the missing values first »), sauf par une fonction d'imputation ; tolérance « somme à 1 » : `1e-6` ; `rng` accepte `None`, un entier ou un `Generator` (`np.random.default_rng(rng)`) (§22) ; le champ `mylearn` d'un exercice nomme **toutes** les fonctions qu'il écrit ;
- examens blancs CP3 à CP6 : types et étoiles selon le §17 ; mini-projet : notebook `mpN_<sujet>.ipynb`, fonctions `mylearn` appelées listées dans `requires` (`syllabus.py check` les vérifie contre les quatre parcours) et dans la section « Ta librairie » du cahier des charges ;
- la lecture d'une fiche publiée se compte à 125 mots par minute (arrondi à 5 min) : après la fiche, `syllabus.py build`, puis l'en-tête « Temps total estimé » et le temps du parcours rapide de la fiche ; ses ⏩ suivent les sections du parcours rapide (un test le vérifie).
- un message `mistakes` ne certifie jamais la valeur d'une autre sous-question (« c'est le z-score de e) ») : il dit où chercher, à la forme interrogative (« vérifie lesquels tu as pris ») ; chaque valeur d'erreur classique se recalcule à partir de l'erreur que décrit son message (session 25 : −0,733 et −0,933 en 12.4 a) ; pour un tableau, « Tous les signes sont inversés » passe désormais avant le comptage par élément ;
- un test de module n'exige que ce que disent la docstring figée, scikit-learn ou la fiche (session 25 : le refus d'un booléen comme `n_components` et des NaN de `MinMaxScaler.transform` retirés) ; une valeur exacte en binaire (3,25) ne teste pas une colonne constante : prendre 0,1 ; une description de données (fiche, data card) se vérifie sur le fichier (`Individual ID` de `penguins_raw` est réutilisé d'une saison et d'une espèce à l'autre).
- une préparation se vérifie sur la **matrice** qu'elle produit, pas seulement sur une accuracy : sur des batches faciles, des colonnes inversées, un scaler appris sur tout ou ddof = 1 gardent une accuracy de 1 (session 26, 12.20) ; un résultat SQL ou pandas trié se vérifie aussi sur sa colonne de clés (un `[5, 1, 5]` se lit dans les deux sens) ;
- un calcul aléatoire caché ne donne jamais une réponse enregistrée : `PCA(n_components=k)` choisit seul un solveur aléatoire sur une grande matrice (imposer `svd_solver="full"`) ; une cellule `record` réutilise les valeurs déjà calculées, elle ne les recalcule pas ;
- un défi sur un fichier brut se sonde contre les **fuites par la saisie** : identifiants, numéros d'échantillon, dates de collecte et ordre des lignes peuvent suivre la cible (A1/A2 des nids de manchots : jusqu'à 0,98) ; on retire ces colonnes et on mélange les lignes ; une règle « chaque ligne se prépare seule » se vérifie aussi sur les lignes incomplètes, et ses appels sont dans un `try` (une erreur de l'apprenant devient une règle non respectée) ; l'état « révélé une fois » survit à la réexécution de sa cellule (`globals().get`) ;
- une cellule de vérification convertit les résultats de l'apprenant dans un `try` (chaîne, flottant, dictionnaire au lieu d'une liste) et ne trace rien tant que le résultat n'a pas la forme attendue ; un message d'échec n'affiche pas la réponse d'une autre vérification (le résultat de pandas en 12.15) ;
- les constantes d'un notebook dont une fonction testée par `wb.run_pytest` peut se servir vont aussi dans le `preamble` du fichier de test (`NUMERIC_32`).
- une réponse qui est une classe ou un label (0, 1, ±1) reçoit ses propres erreurs classiques (les valeurs voisines) : sinon `wb.check` répond « à 1 près » ou « signe inversé », ce qui trahit la réponse ; une valeur numérique de la fiche (même un $e^{-10}$) ne coïncide jamais avec une réponse d'exercice ; un encadré ⚠️ qui corrige le livre sur un exemple repris par un exercice dit que c'est faux sans donner les bons nombres (session 27) ;
- un arbre (ou toute recherche du meilleur candidat) se compare à la référence à l'arrondi près : égalités jugées avec `> meilleur + 1e-12`, et une accuracy de l'arbre de l'apprenant se vérifie avec une tolérance (session 27) ; une comparaison à scikit-learn évite les nœuds minuscules (sans limite, deux features y ont souvent le même gain, que scikit-learn départage au hasard : `max_depth`, `min_samples_split` ou `min_samples_leaf`) (session 28).
- les prédictions d'un 🔮 sont vérifiées par des `wb.check` **à la fin de la cellule d'expérience gardée** (sinon leurs réponses et leurs erreurs classiques ne servent jamais) ; la cellule « dans tes notes » visible avant l'expérience ne suppose aucune issue (« pourquoi des données en plus changent-elles si peu ? » la donne) (session 28) ;
- une cellule de vérification 🔨 affiche ses comparaisons dans `with checked(id)` (une erreur du code de l'apprenant devient une ligne ❌ au lieu d'arrêter la cellule) et lance les tests dans un bloc séparé `if written(sonde)` (⏳ tant que la sonde lève `NotImplementedError` : « Run all » d'un notebook vide n'affiche aucune liste d'échecs) ; une valeur rendue par une fonction de l'apprenant se valide (None, liste au lieu de tuple, forme, unités) avant tout calcul (session 28) ;
- une réponse entière choisie dans une liste (`choices`) reçoit un message pour **chaque** autre valeur de la liste et un `fractional` (« est-ce une accuracy ? ») : sinon `wb.check` arrondit une accuracy à 0 ou 1 et répond le message d'une autre valeur (session 28) ;
- une mesure de temps se vérifie par sa forme (la plus petite de plusieurs durées : une sonde dont le premier appel est bien plus lent) et jamais par sa valeur ; une affirmation de vitesse (« des dizaines de fois plus lent ») se relit contre les sorties exécutées, et se formule avec une fourchette quand elle dépend de la machine (session 28) ;
- une variante ne donne pas le résultat d'un 🔮 suivant (13.12 sur des lunes donnait Naïve Bayes sur des lunes, la question b) de 13.27) (session 28).
- une probabilité de succès d'un votant se note $q$ (pas $p$, le nombre de features) ; un mini-exemple de la fiche change de **cas** et pas seulement de nombres quand un exercice papier refait le même calcul (session 29 : AdaBoost s'arrête aux poids non normalisés, le gradient boosting prend une feuille de deux exemples) ; un fait historique repris du livre se vérifie aussi (Apollo) ;
- un test qui dépend d'un tirage de l'apprenant (bootstrap) ne pose pas la condition sur une seule ligne : une NaN sur une ligne échappe à deux bootstraps une fois sur huit (session 29).
- un message `mistakes` pour une valeur qui est la bonne réponse d'une **autre** sous-question dit « relis la question : on demande … », jamais « c'est le R² de test » (session 30) ; une valeur « rang » ou « position » ne doit pas coïncider avec un autre indice visible (l'ordre des colonnes : `row_id` placé en tête en 14.19) ;
- un 🐛 à plusieurs bugs se teste **combinaison par combinaison** (2³ versions partiellement corrigées) : chaque version doit afficher le premier point en échec, sans planter ; un bug qui fait planter la bibliothèque (poids NaN) est attrapé et rattaché à son point (14.23) ;
- une vérification d'un modèle de bibliothèque (XGBoost, LightGBM) contrôle aussi ses réglages et que la valeur saisie vient du test (`abs(valeur - rmse(test, modèle.predict))`), car une vérification à 2 décimales laisse passer une fenêtre d'environ 0,01 ; une affirmation de robustesse d'un 🔮 donne ses tranches de données, et ses intervalles de choix laissent une marge sur au moins quatre tirages (14.21 b : seuil 0,005, gains de 0,010 à 0,052) ;
- un défi qui reçoit une fonction de l'apprenant refuse un modèle déjà entraîné ou le même objet rendu deux fois (`check_is_fitted`), signale une RMSE trop belle (des variables globales lues) et dit que « révélé une fois » est une règle d'honneur (14.28) ;
- un nombre d'une solution se calcule sur les valeurs non arrondies (14.20 e : 0,5619 − 0,5475 = 0,014, pas 0,562 − 0,547) ; une durée se donne en fourchette.
- une réponse « chaîne » est comparée sans la casse ni la ponctuation : quand la casse ou les tirets bas comptent (`"svc"` contre `"SVC"`, `clf__C` contre `clf_C`), on pose un choix par lettres (15.Q11) ; une réponse entière qui ne s'arrondit pas au plus proche (un nombre d'essais, la taille d'un fold) reçoit un `fractional` (sinon `wb.check` conseille `round`) ; une erreur qui laisse une valeur dans l'espace transformé a son message (15.3) (session 31) ;
- un code de la fiche se vérifie en l'exécutant dans la version du workbook (session 31 : `set_output(transform="pandas")` plantait avec un `OneHotEncoder` creux ; l'ordre `class A(BaseEstimator, ClassifierMixin)` fait perdre le statut de classifieur sans message).
- les lettres a), b), c)… d'un énoncé sont celles des sous-ID vérifiés (`wb.check("15.17h", …)`) : une variable intermédiaire (le modèle, la recherche) n'a pas de lettre, chaque valeur vérifiée a la sienne, et les indices, les solutions et les questions « dans tes notes » suivent (session 32) ; une question « dans tes notes » visible avant la réponse ne dit pas le résultat (« compare e) et f) », pas « pourquoi sont-ils égaux ? ») ;
- un tracé de vérification ne s'affiche qu'une fois les réponses qu'il montre saisies (`if filled(...)`) ; une réponse de forme inattendue (dictionnaire, chaîne, objet non entraîné) donne une ligne ❌, jamais une trace d'erreur (`np.asarray` dans un `try`, `hasattr(obj, "components_")`) ; `wb.attempt` ne rattrape que `NotImplementedError` et les `TypeError` d'un `None` (session 32) ;
- une réponse de recherche qui dépend d'un ex aequo dit sa règle dans l'énoncé (« à égalité, le plus petit degré, comme `idxmax` ») et reçoit l'autre ex aequo comme erreur classique (15.22, 15.23) ; une affirmation « les mêmes classes » se vérifie point par point, fold par fold (15.18 : à `alpha = 10`, deux points changent de classe dans un fold, l'un devient juste et l'autre faux) ;
- le contrôle anti-fuite d'un défi qui reçoit une fonction de l'apprenant réentraîne sa méthode sur des labels mélangés **en mélangeant aussi, le temps du contrôle, les variables globales qui contiennent la cible** (`Y_31`, `DATA_31`, `RAW_31`, restaurées dans un `finally`) ; il compare les prédictions aux labels mélangés et aux vrais (une méthode honnête reste vers 0,5 pour les deux) : un contrôle sur les seuls labels mélangés laisse passer une méthode qui lit `Y_31` (15.31) ;
- un 🐛 « adaptateur » vérifie aussi que `__init__` ne range que ses arguments (`vars(objet)`), et son premier diagnostic reproduit l'appel que fait `cross_val_score` (`clone` avec les arguments par défaut), pour afficher le symptôme décrit par la solution (15.29).
- une valeur enregistrée ne dépend jamais du flux aléatoire exact d'une fonction de l'apprenant quand le contrat ne fixe pas ce flux (16.23 : la part des neurones morts change avec l'ordre des tirages de `init_weights` ; une fourchette, pas un `wb.check`) ; un exemple de format (`"(3, 5)"`) ne coïncide pas avec une réponse du 🔮 ; une figure fournie qui mélange des panneaux construit leur correspondance sans l'écrire en clair (permutation à graine, 16.22) ;
- une précision du contrat « que vérifient les tests » a son test (session 34 : le refus d'un booléen comme taille, d'un `x` 3-D et d'un `W` 1-D ajoutés aux tests du ch. 16) ;
- les exemples d'un tableau de la fiche (systèmes synchrones et asynchrones, pièges) ne reprennent ni les items d'un quiz ni les réseaux d'un exercice (Q5, Q1b, 16.1 e) ; une phrase de la fiche qui cite le livre se met entre guillemets avec sa page (« leur influence initiale s'efface rapidement », p. 668) ;
- un défi dont la réussite dépend d'un réglage fin (16.24) se calibre sur dix graines, et sa solution donne la méthode la plus robuste trouvée, avec ce que donnent les autres (un apprenant simulé a trouvé mieux que la première référence : le biais décalé de +0,5 écart-type).

- une porte avant une action irréversible (le coffre du test) compte aussi les cellules interrompues : `checks_of` marque la cellule en échec jusqu'à `checks_done()`, placé à la fin du bloc `wb.attempt` ; une variable tirée d'une décision refusée (le pipeline final) est retirée, pour qu'une étape suivante ne s'appuie pas sur l'ancienne (MP3.5, session 33) ;
- une vérification de code d'examen appelle chaque fonction de l'apprenant dans un `try`, petits cas compris, et repart de copies vierges des données (`_ORIGINALS` : ⚠️ si un essai les a modifiées) ; une erreur classique sans effet sur la valeur demandée (k choisi sur le test, scaler appris hors du pipeline) se teste sur un second jeu où elle change le résultat (4 000 autres districts en CP3.6) ; une règle « le premier dans l'ordre reçu » se teste avec un ordre non trié, et un paramètre ignoré avec d'autres valeurs de ce paramètre (CP3.7) ;

## 🧠 Quiz

### 15.Q1 — Coder soi-même ou utiliser une bibliothèque ?
a) **Faux** : le livre choisit la bibliothèque, pour se concentrer sur les décisions de machine learning plutôt que sur la programmation (fiche §15.1). b) **A** : une bibliothèque garantit la qualité de son code, pas l'adéquation du modèle à tes données ; il faut toujours comprendre et régler. c) **Vrai** : NumPy pour les tableaux et l'algèbre linéaire, SciPy pour le reste (fiche §15.2). d) **B** : PyTorch, à partir du ch. 20 ; scikit-learn ne vise pas les grands réseaux ni le GPU.
**À retenir** : scikit-learn, c'est le machine learning classique, sur des données qui tiennent en mémoire, derrière une interface commune ; tu sais ce qu'il cache, puisque tu en as écrit une partie dans `mylearn`.

### 15.Q2 — Importer proprement et lire une dépréciation
a) **B** : `from sklearn import linear_model` crée le nom du **module** ; la classe s'écrit `linear_model.Ridge()`. b) **B** : l'argument marche encore en 1.6 et en 1.7, et disparaîtra en 1.8. c) **Faux** : entre 0.19 et 1.6, des paramètres ont été retirés (`base_estimator`, `normalize`), des fonctions aussi (`load_boston`), et des défauts ont changé (`cv`, `n_init`). d) **B** : la documentation de **ta** version dit par quoi remplacer l'appel ; masquer l'avertissement ne fait que retarder la panne. e) **Faux** : `stable` suit la dernière version publiée (1.9 en 2026) ; pour Colab, lis `scikit-learn.org/1.6/`, et vérifie ta version avec `sklearn.__version__`.
**À retenir** : un `FutureWarning` est une information datée (« déprécié en X, retiré en Y ») : modernise l'appel dès qu'il apparaît.

### 15.Q3 — Hyperparamètres au constructeur, attributs appris avec « _ »
a) **B** : tu le fixes avant l'apprentissage. b) **Faux** : `coef_` n'existe qu'après `fit` (sinon `AttributeError`). c) **Vrai** : `get_params()` renvoie `{"alpha": 2.0, "fit_intercept": True, …}`. d) **B** : `clone` relit les hyperparamètres et crée un objet neuf, non entraîné ; c'est ainsi que les recherches et les validations croisées fabriquent leurs modèles. e) **Faux** : le constructeur range ses arguments, sans voir de données ; la vérification et l'apprentissage ont lieu dans `fit`.
**À retenir** : constructeur = réglages ; `fit` = apprentissage ; `nom_` = appris.

### 15.Q4 — Ce que renvoient fit et predict
a) **C** : `fit` renvoie l'objet, ce qui permet d'enchaîner `.fit(X, y).predict(X_new)`. b) **B** : `(100, 1)`, une ligne par exemple, une colonne par feature, même pour une seule feature. c) **A** : `(5,)`, une prédiction par exemple, dans un tableau à une dimension. d) **Faux** : `ValueError: Expected 2D array, got scalar array instead` ; il faut `predict([[3.0]])`. e) **Faux** : un second `fit` repart de zéro (sauf `warm_start` ou `partial_fit`).
**À retenir** : `X` toujours en deux dimensions, à l'entraînement comme à la prédiction ; `y` et les prédictions en une dimension.

### 15.Q5 — decision_function ou predict_proba ?
a) **A** : `(4,)`, un seul score par exemple, celui de la classe `classes_[1]`. b) **C** : `(4, 2)`, une probabilité par classe. c) **C** : `(4, 3)`, un score par classe au-delà de deux classes. d) **0,5** : $\sigma(0) = 1/(1 + 1)$. e) **Faux** : `RidgeClassifier` n'a qu'un `decision_function`, son score n'ayant pas de lecture probabiliste. f) **Vrai** : les probabilités de `SVC(probability=True)` viennent d'une calibration interne, faite par validation croisée, et la documentation prévient qu'elles peuvent contredire `predict` près de la frontière.
**À retenir** : à deux classes, un score par exemple ; la sigmoïde le traduit en probabilité pour une régression logistique, pas pour tous les modèles.

### 15.Q6 — KMeans : n_clusters, labels_ et choix de k
a) **8**. b) **Faux** : `fit` lit le nombre de features dans `X`. c) **B** : le numéro de cluster de chaque exemple d'entraînement ; les centres sont dans `cluster_centers_`, l'inertie dans `inertia_`. d) **Faux** : la plus petite inertie s'obtient avec un centre par point (inertie nulle), un découpage sans intérêt ; on cherche un coude, ou la meilleure silhouette. e) **B** : DBSCAN regroupe par densité et marque le bruit −1.
**À retenir** : le nombre de clusters est un hyperparamètre ; aucun critère ne le choisit seul, il faut regarder le résultat (le livre le dit).

### 15.Q7 — fit, transform, fit_transform, inverse_transform
a) **B** : `transform` applique ce qui a été appris sur l'entraînement. b) **1,25** : $(70 - 20)/40$ ; une valeur au-delà du maximum de l'entraînement sort de $[0, 1]$, c'est normal. c) **−0,25** : $(10 - 20)/40$. d) **50** : $20 + 40 \times 0{,}75$. e) **Faux** : `PolynomialFeatures`, `Normalizer`, `KMeans` n'en ont pas (fiche, encadré ⚠️ du §15.6.1).
**À retenir** : `fit` sur l'entraînement, `transform` partout ; `fit_transform` seulement sur l'entraînement.

### 15.Q8 — Ce que la PCA fait vraiment aux features
a) **B** : chaque composante est une combinaison linéaire des features centrées. b) **Faux** : elle ne supprime aucune feature d'origine, elle en construit de nouvelles et garde les premières ; supprimer des features, c'est la sélection de features. c) **Vrai** : le blanchiment divise chaque composante par son écart-type. d) **Faux** : les directions (`components_`) ne changent pas, seule l'échelle des sorties change. e) **Faux** : la PCA est non supervisée ; elle ignore `y`, et peut donc écarter une direction de faible variance très utile pour prédire.
**À retenir** : PCA = de nouvelles features, combinaisons des anciennes ; blanchiment = mêmes directions, variance 1.

### 15.Q9 — Un ensemble est un estimateur comme les autres
a) **Vrai** : `fit`, `predict`, `score`, et il entre dans une validation croisée ou une recherche. b) **B** : `estimator` (renommé en 1.2, `base_estimator` retiré en 1.4). c) **B** : une souche, `DecisionTreeClassifier(max_depth=1)`. d) **Faux** : `n_estimators` est un maximum ; AdaBoost s'arrête dès qu'un membre est parfait sur l'entraînement, ou quand un membre ne fait pas mieux que le hasard. e) **B** : un vote pondéré par les $\alpha_m$ (ch. 14).
**À retenir** : compte les membres gardés avec `len(model.estimators_)` avant de commenter un ensemble.

### 15.Q10 — Grille ou recherche aléatoire ?
a) **B** : c'est toi qui le fixes avant `fit`. b) **Faux** : la recherche ne fait que lancer les entraînements ; seul `n_jobs` (plusieurs cœurs) fait gagner du temps. c) **24** : $3 \times 4 \times 2$. d) **10**. e) **Vrai** : une grille 3 × 3 n'essaie que trois valeurs de l'hyperparamètre important, neuf tirages en essaient neuf (Bergstra et Bengio). f) **Vrai** : une uniforme entre 0,001 et 1 000 tire sous 1 environ une fois sur mille ; `loguniform` donne autant de chances à chaque ordre de grandeur.
**À retenir** : le coût d'une grille est un produit ; la recherche au hasard dépense ses essais là où ils comptent, sur des distributions bien choisies.

### 15.Q11 — Pipeline : step__param et absence de fuite
a) **D** : `"clf__C"`, le nom de l'étape (`clf`), deux tirets bas, le nom de l'hyperparamètre. b) **Vrai** : le pipeline entier est cloné et réappris sur les folds d'entraînement de chaque tour. c) **B** : le fold de validation n'est que transformé, avec le scaler appris sur les autres folds. d) **B** : `"svc"`, le nom de la classe en minuscules ; `"SVC"` serait refusé dans une grille (`SVC__C` n'existe pas). e) **Faux** : la dernière étape peut être n'importe quel estimateur, un classifieur le plus souvent ; les étapes **précédentes** doivent être des transformateurs.
**À retenir** : `étape__paramètre`, et `pipe.get_params().keys()` pour vérifier les noms.

### 15.Q12 — Datasets, train_test_split et documentation
a) **0,25**. b) **Vrai** : `shuffle=True` par défaut, pour qu'un fichier ordonné ne donne pas un test différent de l'entraînement. c) **B** : `stratify=y`. d) **Faux** : retiré en 1.2 (fiche, encadré 🕰️ du §15.10). e) **38** : $0{,}3 \times 125 = 37{,}5$, arrondi au-dessus ; l'entraînement a les 87 autres. f) **B** : `make_circles`.
**À retenir** : `train_test_split(X, y, test_size=…, stratify=y, random_state=…)`, et une coupe sans mélange pour des données temporelles.

## 🔁 Rappels

### 15.R1 — Ch. 14 : Forêt aléatoire ou gradient boosting ?
a) **A** : la forêt ; ses arbres ne dépendent pas les uns des autres et s'entraînent en parallèle. b) **Faux** : une forêt ne surapprend pas en ajoutant des arbres, elle cesse seulement de progresser. c) **A** : le biais, en combinant des apprenants faibles. d) **B** : `learning_rate`. e) **Faux** : le score out-of-bag est celui du bagging et des forêts ; un gradient boosting n'en a que s'il sous-échantillonne (`subsample` < 1), ce qui n'est pas son défaut.
**À retenir** : forêt = arbres indépendants, variance réduite, peu de réglages ; gradient boosting = arbres en série, biais réduit, learning rate et early stopping.

### 15.R2 — Ch. 12 : Où ajuster le scaler dans une validation croisée ?
a) **Vrai** : la moyenne et l'écart-type ont été calculés avec les folds de validation. b) **B** : les folds d'entraînement du tour. c) **1,5** : $(65 - 50)/10$. d) **Vrai** : c'est l'expérience du ch. 8, refaite au ch. 15 avec un pipeline (🔬 15.24). e) **A** : la médiane est une statistique des données ; le logarithme se calcule ligne par ligne, sans rien apprendre.
**À retenir** : tout ce qui se calcule **sur des lignes** (moyenne, médiane, catégories vues, features sélectionnées) s'apprend dans chaque fold ; un pipeline le fait pour toi.

### 15.R3 — Ch. 8 : Combien de modèles pour une validation croisée à 5 folds ?
a) **5**. b) **1** : chaque exemple est dans un seul fold, mis de côté une fois. c) **4**. d) **201** : $1\,003 = 5 \times 200 + 3$, les trois premiers folds ont 201 exemples, les deux autres 200. e) **40** : un modèle par exemple mis de côté. f) **Vrai**.
**À retenir** : $k$ folds = $k$ modèles ; chaque exemple est validé une fois et sert $k - 1$ fois à l'entraînement.

### Ex 15.1 — Compter les modèles entraînés par une recherche en grille ✏️
**Réponses** : a) **12** · b) **60** · c) **61** · d) **37** · e) **121** · f) **45** · g) **101** · h) **183**.
**Démarche** : a) $4 \times 3 = 12$ candidats. b) Chaque candidat est noté par une validation croisée à 5 folds : $12 \times 5 = 60$. c) Avec `refit=True`, le meilleur réglage est réentraîné une fois sur tout `X_train` : $61$. d) En 0.19, le défaut était de 3 folds : $12 \times 3 + 1 = 37$. e) Trois hyperparamètres, à 5, 2 et 3 valeurs : $30$ candidats, $30 \times 4 + 1 = 121$ entraînements du pipeline (et autant de `PolynomialFeatures` et de `RidgeClassifier`). f) Une liste de grilles additionne : $1 \times 3 = 3$ candidats linéaires, $1 \times 3 \times 2 = 6$ candidats RBF, $9 \times 5 = 45$, sans réentraînement final. g) $20 \times 5 + 1 = 101$. h) Chaque fold extérieur lance une recherche complète de c) sur ses données d'entraînement : $3 \times 61 = 183$ ; `cross_val_score` n'ajoute pas de réentraînement final.
**Dans ta copie** : le réentraînement final donne un modèle appris sur **toutes** les données d'entraînement (et non sur 80 % d'entre elles, comme ceux de la validation croisée), prêt à servir : c'est `best_estimator_`. `best_score_` est le meilleur de douze scores de validation : choisir le maximum de plusieurs scores bruités donne une estimation **optimiste** (le meilleur a eu un peu de chance), et ces folds ont servi à choisir. La validation croisée imbriquée de h) note chaque recherche sur un fold extérieur qu'elle n'a jamais vu : elle estime la performance de la **procédure** « rechercher, puis réentraîner ».
**Erreurs fréquentes** : oublier le réentraînement final (60 au lieu de 61) ; compter un réentraînement final par candidat (72) ; multiplier les deux grilles de f) au lieu de les additionner (90), ou les fusionner en une seule grille (60) ; oublier que chaque fold extérieur de h) refait toute la recherche.
**Variante** : `GridSearchCV(SVC(), {"C": [0.1, 1, 10], "gamma": [0.01, 0.1, 1]}, cv=10)`. Combien d'entraînements ? ($3 \times 3 = 9$ candidats, $9 \times 10 + 1 =$ **91**.)

### Ex 15.2 — De decision_function à predict_proba ✏️
**Réponses** : a) **0,8808** · b) **0,2689** · c) **0,5** · d) **[1, 0, 0, 1, 0]** · e) **2,1972** · f) **1,3863** · g) **1** · h) **0,7054** · i) **Faux** · j) **Faux**.
**Démarche** : a) $\sigma(2) = 1/(1 + e^{-2}) = 1/1{,}1353 \approx 0{,}8808$. b) $\sigma(-1) = 1/(1 + e) \approx 0{,}2689$, soit $1 - \sigma(1)$. c) $\sigma(0) = 0{,}5$. d) À deux classes, `predict` renvoie la classe 1 quand le score est **strictement** positif : 2,0 et 0,5 donnent 1 ; −1,0, 0,0 et −3,2 donnent 0 (le score nul va à la classe 0). e) Le logit : $\ln(0{,}9/0{,}1) = \ln 9 \approx 2{,}1972$. f) $\ln(0{,}8/0{,}2) = \ln 4 \approx 1{,}3863$. g) Seul le score 2,0 dépasse 1,3863 : **1** exemple. h) $e^2 / (e^2 + e^1 + e^{-1}) = 7{,}389 / (7{,}389 + 2{,}718 + 0{,}368) = 7{,}389 / 10{,}475 \approx 0{,}7054$. i) Faux : $e^{s_k + 5} / \sum_j e^{s_j + 5} = e^5 e^{s_k} / (e^5 \sum_j e^{s_j})$, le facteur $e^5$ se simplifie. j) Faux : le score d'un `RidgeClassifier` vient d'une régression sur des cibles −1/+1, sans modèle de probabilité ; sa sigmoïde est un nombre entre 0 et 1, rien ne dit qu'il soit calibré.
**Dans ta copie** : la régression logistique est **construite** pour que $\sigma(s)$ soit une probabilité : elle maximise la vraisemblance des labels sous ce modèle (la log-loss, ch. 6 et 13), et son score est un log-odds. Le `RidgeClassifier` minimise une erreur quadratique : son score classe bien les exemples, mais son échelle n'a rien de probabiliste. Pour en tirer des probabilités, on le **calibre** : `CalibratedClassifierCV(RidgeClassifier(), method="sigmoid")` apprend, par validation croisée, une sigmoïde $\sigma(a s + b)$ adaptée à ses scores (la méthode de Platt), ou une fonction croissante (`method="isotonic"`).
**Erreurs fréquentes** : oublier le signe moins de l'exposant (on trouve alors 0,1192, qui est $\sigma(-2)$) ; classer 1 l'exemple de score nul ; prendre $\ln p$ au lieu du logit, ou $\log_{10}$ ; ne diviser $e^2$ que par $e^2 + e^1$ en h).
**Variante** : deux scores, 1,5 et −0,5. Leurs probabilités, et le score qui correspond à 0,7 ? ($\sigma(1{,}5) \approx$ **0,8176**, $\sigma(-0{,}5) \approx$ **0,3775**, $\ln(0{,}7/0{,}3) \approx$ **0,8473**.)

### Ex 15.3 — Ramener une droite ajustée dans l'espace d'origine ✏️
**Réponses** : a) **0,5** · b) **0,55** · c) **21** · d) **15** · e) **27** · f) **1,5** · g) **19,5** · h) **1,75** · i) **36** · j) **Faux**.
**Démarche** : la mise à l'échelle est $x' = (x + 3)/8$ et $y' = (y - 10)/20$, d'inverse $y = 10 + 20\,y'$. a) $x' = 4/8 = 0{,}5$. b) $y' = 0{,}6 \times 0{,}5 + 0{,}25 = 0{,}55$. c) $y = 10 + 20 \times 0{,}55 = 21$. d) En $x' = 0$ ($x = -3$), $y' = 0{,}25$, donc $y = 15$. e) En $x' = 1$ ($x = 5$), $y' = 0{,}85$, donc $y = 27$. f) La pente entre les deux extrémités : $(27 - 15)/(5 - (-3)) = 12/8 = 1{,}5$. g) $y(0) = 15 + 1{,}5 \times 3 = 19{,}5$ (ou : $x' = 0{,}375$, $y' = 0{,}475$, $y = 19{,}5$). h) $x' = 14/8 = 1{,}75$, hors de $[0, 1]$ : la transformation est celle de l'entraînement, elle ne ramène pas les données nouvelles dans la boîte. i) $y' = 0{,}6 \times 1{,}75 + 0{,}25 = 1{,}3$, $y = 10 + 26 = 36$ (et $19{,}5 + 1{,}5 \times 11 = 36$). j) Faux : `inverse_transform` sur le point $(0{,}6 ;\ 0{,}25)$ donne $(1{,}8 ;\ 15)$, qui n'est ni la pente 1,5 ni l'ordonnée 19,5 : une pente et une ordonnée ne sont pas des coordonnées de points, elles ne se transforment pas comme eux.
**Dans ta copie** : la pente d'origine vaut $a \times \dfrac{\text{étendue de } y}{\text{étendue de } x} = 0{,}6 \times \dfrac{20}{8} = 1{,}5$. Une droite reste une droite parce que les deux transformations sont **affines** : $y = 10 + 20\,(0{,}6\,\frac{x + 3}{8} + 0{,}25)$ est encore de la forme $\alpha x + \beta$. Après une transformation logarithmique de $y$ (on ajuste $\ln y$), la droite ramenée devient une **exponentielle** $y = e^{\alpha x + \beta}$ : une droite dans l'espace transformé n'est plus une droite dans l'espace d'origine, et il faut ramener **beaucoup** de points (ou toute la courbe) pour la tracer.
**Erreurs fréquentes** : appliquer la droite à $x$ au lieu de $x'$ (on trouverait 27 en c) ; oublier d'ajouter le minimum en ramenant $y'$ ; utiliser l'étendue de $x$ pour ramener $y$ ; ramener $x = 11$ à 1, comme si la transformation bornait les données ; transformer la pente comme un point (j).
**Variante** : $x$ va de 0 à 10, $y$ de −5 à 5, et la droite transformée est $y' = 0{,}4\,x' + 0{,}3$. Les extrémités et la pente d'origine ? ($y(0) =$ **−2**, $y(10) =$ **2**, pente $0{,}4 \times 10/10 =$ **0,4** : quand les deux étendues sont égales, la pente ne change pas.)

### Ex 15.4 — Combien de features polynomiales ? ✏️
**Réponses** : a) **6** · b) **21** · c) **5** · d) **45** · e) **165** · f) **1 770** · g) **16** · h) **1,42** · i) **4**.
**Démarche** : a) $\binom{4}{2} = 6$ : $1$, $x$, $y$, $x^2$, $xy$, $y^2$. b) $\binom{7}{5} = 21$. c) Degré exactement 4 en deux variables : $x^4$, $x^3 y$, $x^2 y^2$, $x y^3$, $y^4$, soit 5 ; en général $\binom{p + d - 1}{d} = \binom{5}{4}$. d) $\binom{10}{2} = 45$ : la constante, 8 features, 8 carrés et $\binom{8}{2} = 28$ produits. e) $\binom{11}{3} = 165$. f) $\binom{23}{3} - 1 = 1\,771 - 1 = 1\,770$. g) Sans carré : $\binom{5}{0} + \binom{5}{1} + \binom{5}{2} = 1 + 5 + 10 = 16$. h) $100\,000 \times 1\,771 \times 8 = 1{,}4168 \times 10^9$ octets, soit **1,42** Go. i) $\binom{11}{1} = 11$, $\binom{12}{2} = 66$, $\binom{13}{3} = 286$, $\binom{14}{4} = 1\,001$ : $d = 4$.
**Dans ta copie** : un monôme de degré au plus $d$ s'écrit $x_1^{a_1} \cdots x_p^{a_p}$ avec $a_1 + \dots + a_p \le d$ ; on ajoute $a_0 = d - (a_1 + \dots + a_p) \ge 0$, et l'on compte les suites de $p + 1$ entiers positifs ou nuls de somme $d$ : on aligne $d$ étoiles et $p$ barres, et il suffit de choisir la place des $p$ barres (ou des $d$ étoiles) parmi $p + d$ positions, d'où $\binom{p + d}{d}$. Sans la variable fictive, les monômes de degré exactement $d$ sont les suites de $p$ entiers de somme $d$, soit $\binom{p + d - 1}{d}$, et $\binom{p + d}{d} = \sum_{j=0}^{d} \binom{p + j - 1}{j}$. Avec $p = 2$, $\binom{2 + d}{d} = (d + 1)(d + 2)/2$ : 3, 6, 10, 15, 21, 28, une croissance en $d^2$ ; avec $p$ grand et $d$ fixé, elle est en $p^d / d!$.
**Erreurs fréquentes** : oublier la constante (`include_bias=True`) ; compter $x_1 x_2$ et $x_2 x_1$ deux fois ; prendre $\binom{p + d}{p}$ pour une autre valeur (c'est la même : $\binom{p + d}{p} = \binom{p + d}{d}$) ; garder les carrés avec `interaction_only=True` ; compter les Go en $2^{30}$ octets (1,32).
**Variante** : $p = 3$ et $d = 4$ ; puis $p = 4$, $d = 3$ et `interaction_only=True`. ($\binom{7}{4} =$ **35** ; $1 + 4 + 6 + 4 =$ **15**.)

### Ex 15.5 — Budget d'une recherche d'hyperparamètres 🧮
**Réponses** : a) **15 625** · b) **43,4** · c) **5,4** · d) **2,5** · e) **0,9539** · f) **90** · g) **5** · h) **16,2**.
**Démarche** : a) $5^5 = 3\,125$ combinaisons, chacune sur 5 folds : $15\,625$ entraînements. b) $15\,625 \times 4 = 62\,500$ minutes, soit $62\,500 / 1\,440 \approx 43{,}4$ jours. c) $43{,}40 / 8 \approx 5{,}4$ jours. d) $60 \times 5 \times 4 = 1\,200$ minutes de calcul, réparties sur 8 cœurs : 150 minutes, soit 2,5 h. e) $1 - 0{,}95^{60} = 1 - 0{,}0461 \approx 0{,}9539$. f) $\ln 0{,}01 / \ln 0{,}95 \approx 89{,}8$, donc 90 essais. g) Tour par tour, en « entraînements sur toutes les données » : $81 \times \frac{1}{81} + 27 \times \frac{3}{81} + 9 \times \frac{9}{81} + 3 \times \frac{27}{81} + 1 \times 1 = 1 + 1 + 1 + 1 + 1 = 5$ ; chaque tour coûte autant, car il garde trois fois moins de candidats avec trois fois plus de données. h) $81 / 5 \approx 16{,}2$.
**Dans ta copie** : le livre : $6^4 = 1\,296$ combinaisons, à une heure chacune, font $1\,296$ heures, soit 54 jours (sans compter les folds : avec une validation croisée à 3 folds, ce serait trois fois plus). Hypothèses fragiles : le temps d'entraînement n'est pas constant d'un réglage à l'autre (1 000 arbres coûtent dix fois plus que 100, une profondeur de 10 bien plus qu'une profondeur de 3) ; le parallélisme n'est jamais parfait (mémoire, copies des données, autres processus) ; « 5 % meilleurs » se mesure dans l'espace **tel qu'on l'échantillonne** : avec une mauvaise distribution (uniforme au lieu de log), la zone utile peut occuper bien moins de 5 % ; et le successive halving suppose qu'un candidat bon sur peu de données reste bon sur beaucoup, ce qui peut être faux pour les modèles dont la capacité utile grandit avec les données.
**Erreurs fréquentes** : oublier les folds ; écrire $5 \times 5$ au lieu de $5^5$ ; convertir les minutes en jours en divisant par 24 ou par 60 seulement ; additionner les probabilités des essais ($60 \times 0{,}05 = 3$) au lieu de passer par le complément ; tronquer $n$ (89) au lieu d'arrondir au-dessus.
**Variante** : 4 hyperparamètres à 4 valeurs, 10 folds, 2 minutes par entraînement, un cœur ; puis le nombre d'essais au hasard pour toucher les 2 % meilleurs avec une probabilité de 0,95. ($4^4 \times 10 = 2\,560$ entraînements, $5\,120$ minutes, soit **3,6** jours ; $\ln 0{,}05 / \ln 0{,}98 \approx 148{,}3$, soit **149** essais.)

### Ex 15.6 — Le Pipeline expliqué en 5 lignes 🗣️
**Réponse modèle** : « Un pipeline, c'est une chaîne de montage : chaque poste (imputer, mettre à l'échelle, encoder) est réglé une fois sur les pièces d'entraînement, puis traite toutes les pièces de la même façon, et le dernier poste, le modèle, prédit. Quand tu l'entraînes, chaque étape apprend ses réglages puis transforme les données pour la suivante ; quand tu prédis, chaque étape ne fait qu'appliquer ses réglages. Si tu le passes à `cross_val_score`, il est **réentraîné entièrement à chaque tour**, sur les seuls folds d'entraînement, et le fold de validation n'est que transformé. Toi, tu standardises avant la validation croisée : la moyenne et l'écart-type ont vu les folds de validation, qui ne jouent plus le rôle de données nouvelles, et ton score est un peu trop beau. Pour une mise à l'échelle sur beaucoup d'exemples, l'écart est petit ; pour une étape qui regarde la cible, comme une sélection de features, il peut faire passer du bruit pur pour un bon modèle. »
**Ce qui compte** : la séparation apprendre / appliquer ; le réapprentissage dans chaque fold ; la cause de l'optimisme (des lignes de validation qui ont servi à préparer) ; l'ordre de grandeur selon l'étape.
**Erreurs fréquentes** : présenter le pipeline comme un simple raccourci d'écriture ; dire qu'il « évite de standardiser le test » (il le standardise, avec les statistiques de l'entraînement) ; affirmer que la fuite d'un scaler est toujours énorme.
**Variante** : explique en deux lignes pourquoi le même pipeline sert aussi en production. (« Parce qu'il garde, dans un seul objet, les réglages appris sur l'entraînement : en production, `predict` applique exactement le même prétraitement qu'à l'entraînement, sans risque d'oublier une étape ni de la réapprendre sur les données reçues. »)

### Ex 15.7 — Boston Housing : un dataset retiré pour raisons éthiques ⚖️
**1.** La feature part de la proportion d'habitants noirs de chaque ville au recensement de 1970. Harrison et Rubinfeld (une étude de 1978 sur le prix que les ménages accordent à un air propre) s'attendaient à une relation **parabolique** avec les prix : à proportion faible ou moyenne, les prix baisseraient si les habitants blancs voyaient leurs voisins noirs comme indésirables ; à proportion très élevée, la discrimination du marché les ferait remonter. Le minimum de la parabole, $B_k = 0{,}63$, est le « seuil » où la tendance s'inverserait. La forme $1\,000\,(B_k - 0{,}63)^2$ inscrit donc dans la donnée elle-même une hypothèse sur la ségrégation, pour laquelle, rappelle Carlisle en citant Kain et Quigley (1975), il n'y avait aucune preuve systématique ; l'avertissement de scikit-learn ajoute que l'étude ne l'a pas démontrée. Elle n'est pas inversible, parce que deux proportions symétriques autour de 0,63 (0,5 et 0,76, par exemple) donnent la même valeur de $B$ : sans les données d'origine, on ne peut plus savoir de quel côté du seuil se trouve une ville (Carlisle compte 36 lignes ambiguës sur 506), ni tester une autre hypothèse.
**2.** Parce que le problème n'est pas qu'une colonne : c'est un dataset construit pour une question et selon des choix qu'on ne voit pas en le chargeant, enseigné pendant des décennies comme un exemple neutre de « prix de l'immobilier ». Les modèles publiés et les « bons scores » ont été obtenus avec $B$, d'autres colonnes portent les mêmes inégalités (la composition sociale, `LSTAT`), et l'utiliser sans contexte apprend surtout à ne pas regarder d'où viennent les données. Carlisle ne propose d'ailleurs pas de supprimer la colonne, mais de la comprendre : bien documentée, elle aiderait à mesurer ce que la discrimination a coûté. Les mainteneurs en déconseillent fortement l'usage, sauf pour étudier et enseigner ces questions.
**3.** Le cycle de dépréciation (avertissement en 1.0, retrait en 1.2) laisse le temps de migrer, explique pourquoi, et propose des remplaçants (California, Ames) ; personne ne découvre le changement par un plantage. **4.** California Housing vient du recensement américain de **1990** : des prix d'il y a plus de trente ans ; son unité est le **groupe d'îlots** (*block group*), pas le logement, avec des moyennes par ménage parfois extrêmes (résidences, logements vacants) ; la cible est **plafonnée** (à 5, soit 500 000 $), comme l'âge médian des logements (52 ans) et le revenu médian (15). Il ne contient pas de variable raciale, mais la géographie (latitude, longitude) reflète des ségrégations réelles : un modèle de prix peut les reproduire.
**5.** Exemples de questions : *Qui a collecté ces données, quand, et pour répondre à quelle question ?* *Comment chaque variable a-t-elle été construite (unités, transformations, variables calculées), et une data card le documente-t-elle ?* *Quels groupes de personnes sont concernés, et quelles conséquences aurait un modèle qui reproduit les régularités de ces données ?*
**Erreurs fréquentes** : réduire le problème à « une colonne raciale à supprimer » ; présenter California comme exempt de limites ; confondre la dépréciation (un délai annoncé) et la suppression.
**Variante** : un collègue propose de recréer Boston Housing depuis la source d'origine pour un cours d'introduction à la régression. Que lui réponds-tu ? ### Ex 15.8 — Lire l'article sur la conception de l'API de scikit-learn 📄
**1.** Cinq principes (section 2.1). **Cohérence** : tous les objets partagent une interface faite de quelques méthodes (`fit`, `predict`, `transform`) ; exemple : `KMeans`, `Ridge` et `MinMaxScaler` s'entraînent tous avec `fit`. **Inspection** : les hyperparamètres et ce qui est appris sont des attributs publics ; exemple : `alpha`, `coef_`, `cluster_centers_`. **Pas de prolifération de classes** : seuls les algorithmes ont leurs classes ; les données sont des tableaux NumPy ou des matrices creuses SciPy, les hyperparamètres des nombres ou des chaînes ; exemple : `solver="svd"`. **Composition** : on construit des traitements en enchaînant des briques ; exemple : `make_pipeline(PolynomialFeatures(), StandardScaler(), RidgeClassifier())`. **Valeurs par défaut raisonnables** : exemple : le livre qui laisse presque tout par défaut et obtient une baseline.
**2.** L'**estimateur** apprend avec `fit` ; le **prédicteur** ajoute `predict` (et souvent `score`, `predict_proba`) ; le **transformateur** ajoute `transform` (et `fit_transform`). Le constructeur ne fait que ranger les hyperparamètres : il ne voit aucune donnée et n'apprend rien, ce qui permet de créer, copier et régler des modèles **avant** d'avoir des données. Des hyperparamètres publics se lisent et se changent de l'extérieur (`get_params`, `set_params`) : c'est ce qu'exploitent les recherches d'hyperparamètres et `clone`.
**3.** En tableaux NumPy (denses) ou en matrices creuses SciPy, de forme (exemples, features). Pas de conversion vers un format maison : les données s'échangent directement avec NumPy, SciPy, pandas et le reste de l'écosystème, et l'interface reste petite. Contrepartie : pas de noms de colonnes ni de types hétérogènes dans le tableau lui-même (ce que `ColumnTransformer` et `set_output` ont comblé depuis).
**4.** Un méta-estimateur est un estimateur construit à partir d'autres (un pipeline, un ensemble, une recherche d'hyperparamètres, un un-contre-tous). Comme tous les objets ont `fit`, `predict`, `get_params` et `set_params`, un `GridSearchCV` peut cloner n'importe quel estimateur, changer ses hyperparamètres et le noter par validation croisée sans rien savoir de lui ; un pipeline expose les hyperparamètres de ses étapes sous la forme `étape__paramètre`, et devient lui-même un estimateur qu'on règle comme un autre.
**5.** Le *duck typing* juge un objet à ses méthodes, pas à ses ancêtres : on peut écrire un estimateur compatible sans dépendre de scikit-learn. La limite pratique : les outils de scikit-learn s'appuient aussi sur des méthodes et des conventions moins visibles (`get_params`, `set_params`, le type d'estimateur pour stratifier les folds) ; une classe de `mylearn`, qui a `fit` et `predict` mais pas `get_params`, est refusée par `cross_val_score` (🐛 15.29), et `BaseEstimator` est le moyen simple de les obtenir.
**6.** L'article reconnaît plusieurs limites : des données représentées par de simples tableaux NumPy ou des matrices creuses, ce qu'il admet pouvoir sembler rudimentaire, et des objets qui ne sont pas optimisés pour prédire un exemple à la fois ; un parallélisme difficile en Python, limité à des tâches grossières comme une recherche en grille parallèle ; **pas de solution durable pour sauvegarder un modèle** : `pickle` n'est qu'un format de fichier, sans compatibilité d'une version à l'autre, et charger un fichier inconnu peut exécuter du code ; des algorithmes classiques encore absents (réseaux de neurones, ensembles par bagging, complétion des valeurs manquantes) ; et un estimateur et son modèle appris réunis dans un seul objet, qui complique l'envoi d'un modèle dans un autre environnement (il évoque un export PMML). Depuis : `joblib` et `n_jobs` parallélisent les validations croisées et les recherches, et plusieurs algorithmes sont compilés avec OpenMP ; `MLPClassifier`, `BaggingClassifier` et les imputeurs (`SimpleImputer`, `KNNImputer`) sont arrivés ; la sauvegarde s'est enrichie de `skops` et d'ONNX ; `pickle`, `joblib` et `skops` restent **sans compatibilité entre versions** (d'où l'`InconsistentVersionWarning`), et ONNX contourne le problème en ne servant qu'à prédire. L'article ne parle pas des données hétérogènes ni des noms de colonnes : `ColumnTransformer` (0.20), `get_feature_names_out` (1.0) et `set_output` (1.2) y ont répondu.
**Erreurs fréquentes** : réciter les cinq principes sans exemple ; confondre estimateur et prédicteur (un scaler est un estimateur, pas un prédicteur) ; croire que l'héritage de `BaseEstimator` est obligatoire.
**Variante** : quel principe la classe `RidgeClassifierCV` illustre-t-elle, et lequel semble-t-elle contredire ? (Elle illustre la cohérence : on l'utilise comme un `RidgeClassifier`, avec `fit` et `predict`. Elle semble contredire la non-prolifération des classes, puisqu'elle double une classe existante ; l'article n'en parle pas ; la documentation la justifie par l'efficacité, une validation croisée « propre au modèle » : elle choisit `alpha` bien plus vite qu'une recherche générale, grâce à un calcul propre à Ridge.)

## 💼 Entretien

### 15.E1 — fit, transform, predict : pourquoi jamais fit sur le test ?
**Réponse modèle en 60 secondes** : « `fit` apprend à partir des données : les coefficients d'un modèle, ou les statistiques d'une transformation, comme la moyenne et l'écart-type d'un scaler. `transform` applique une transformation déjà apprise, à n'importe quelles données. `fit_transform` fait les deux d'un coup, et ne s'utilise que sur l'entraînement. `predict` applique un modèle déjà appris. Le test doit jouer le rôle de données nouvelles, que le système n'a jamais vues : si je fais un `fit` dessus, je réapprends une transformation différente de celle que le modèle a apprise à lire, et en plus le test influence la préparation, donc l'évaluation devient optimiste. La règle, c'est `fit` sur l'entraînement seul, `transform` partout ; en pratique je mets tout dans un `Pipeline`, ce qui le garantit en validation croisée comme en production. »
**Relances possibles** : « Et pour la validation croisée ? » (le pipeline est réappris dans chaque fold ; un prétraitement fait avant est une fuite) · « Un `fit_transform` sur tout le dataset avant le découpage, c'est grave ? » (souvent peu pour une simple mise à l'échelle sur beaucoup de lignes, énorme pour une sélection de features ou un encodage qui utilise la cible) · « Et en production, sur un seul exemple ? » (on ne réapprend rien : un `fit` sur une seule ligne donnerait une moyenne égale à cette ligne).

### 15.E2 — Grille, hasard ou optimisation bayésienne ?
**Réponse modèle en 60 secondes** : « Avec une dizaine d'hyperparamètres, une grille est hors de prix : même trois valeurs chacun font 59 049 combinaisons, à multiplier par les folds. Je commence par une recherche au hasard, avec des distributions adaptées, log-uniformes pour le learning rate ou la régularisation, et un budget fixé, une soixantaine d'essais par exemple : Bergstra et Bengio ont montré qu'elle trouve d'aussi bons réglages qu'une grille pour une fraction du coût, parce que peu d'hyperparamètres comptent vraiment. Si le budget est serré, j'utilise un successive halving, qui abandonne tôt les réglages sans avenir, ou Optuna, qui choisit en plus chaque essai d'après les précédents. Pour un gradient boosting, je règle aussi le nombre d'arbres par early stopping plutôt que dans la grille. Enfin, le meilleur score de la recherche est optimiste : j'évalue le modèle retenu sur un test mis de côté avant la recherche, ou par validation croisée imbriquée. »
**Relances possibles** : « Pourquoi une distribution log ? » (une régularisation à 0,001 ou à 0,01 change autant le modèle qu'à 10 ou 100 : il faut autant d'essais par ordre de grandeur) · « Combien d'essais au hasard ? » ($1 - (1 - q)^n$ : 60 essais touchent les 5 % meilleurs réglages avec une probabilité d'environ 95 %) · « Quels hyperparamètres d'abord ? » (learning rate et nombre d'arbres, puis profondeur ou nombre de feuilles, puis régularisation et sous-échantillonnage).

### 15.E3 — Pipeline et ColumnTransformer sur des données hétérogènes
**Réponse modèle en 60 secondes** : « Je construis une branche par type de colonne. Pour les numériques : une imputation, par la médiane par exemple, puis un `StandardScaler`. Pour les catégorielles : une imputation par la valeur la plus fréquente, ou une catégorie « manquant », puis un `OneHotEncoder(handle_unknown="ignore")`, pour qu'une catégorie inconnue en production ne fasse pas planter. Un `ColumnTransformer` applique chaque branche à ses colonnes, choisies par nom ou par type avec `make_column_selector`, et met les résultats côte à côte ; je le place dans un `Pipeline` avec le modèle. Deux raisons : tout ce qui apprend des données (médianes, catégories, moyennes) est réappris dans chaque fold, donc pas de fuite en validation croisée ; et j'ai un seul objet à régler par recherche d'hyperparamètres, à sauvegarder et à déployer. J'ajoute `set_output(transform="pandas")` pour garder les noms de colonnes et inspecter ce que reçoit le modèle. »
**Relances possibles** : « Et pour un arbre ou un gradient boosting ? » (pas besoin de mise à l'échelle ; un `OrdinalEncoder` suffit souvent, et `HistGradientBoosting` gère les catégories et les valeurs manquantes lui-même) · « Une catégorie à 10 000 valeurs ? » (regrouper les rares avec `min_frequency`, ou un `TargetEncoder`, qui fait sa propre validation croisée interne pour éviter la fuite) · « Comment retrouver le nom des features ? » (`get_feature_names_out()`).

### 15.E4 — predict_proba donne-t-il une vraie probabilité ?
**Réponse modèle en 60 secondes** : « Pas forcément. `predict_proba` donne un nombre entre 0 et 1 qui **classe** bien les clients si le modèle est bon, mais il n'est une vraie probabilité que s'il est **calibré** : parmi les clients à qui le modèle donne 0,8, environ 80 % doivent résilier. Je le vérifie sur un jeu de validation avec une courbe de calibration, ou le score de Brier. Une régression logistique est souvent assez bien calibrée ; un SVM, un Naïve Bayes ou une forêt beaucoup moins. Si besoin, je calibre avec `CalibratedClassifierCV`, par une sigmoïde ou une régression isotone, par validation croisée. Ensuite, le seuil de décision ne doit pas rester à 0,5 par défaut : je le choisis sur la validation d'après le coût d'une fausse alerte et d'une résiliation manquée, à la main ou avec `TunedThresholdClassifierCV`. »
**Relances possibles** : « La calibration change-t-elle l'AUC ? » (presque pas : elle garde l'ordre des scores ; elle change leur valeur) · « Pourquoi une forêt est-elle mal calibrée ? » (ses probabilités sont des moyennes de votes d'arbres, qui atteignent rarement 0 ou 1) · « Classes déséquilibrées ? » (mesurer avec la precision, le recall et l'aire precision-recall, et ne rééchantillonner que l'entraînement).

### 15.E5 — Mettre un modèle scikit-learn en production
**Réponse modèle en 60 secondes** : « Je pars du **pipeline** retenu, prétraitement compris, réentraîné sur toutes les données d'entraînement. Je le sauvegarde avec `joblib`, et à côté un fichier de métadonnées : les versions de scikit-learn, NumPy, SciPy et Python, une référence aux données d'entraînement, le score de validation et la date. J'épingle l'environnement avec un `requirements.txt` ou une image Docker, parce qu'un fichier `joblib` ne se recharge de façon fiable qu'avec les mêmes versions ; scikit-learn le signale d'ailleurs par un `InconsistentVersionWarning`. Je sers le modèle derrière une petite API, qui le charge une fois au démarrage et valide les entrées. Je ne charge jamais de fichier `pickle` d'une source inconnue : pour partager un modèle, `skops` ou ONNX sont plus sûrs. Enfin, je surveille les entrées et les performances, pour réentraîner quand les données dérivent ; et je versionne le code dans git et les données par une référence fixe (une empreinte, un outil comme DVC), pour que le résultat se rejoue dans six mois. »
**Relances possibles** : « Pourquoi pas seulement le modèle, sans le pipeline ? » (le prétraitement fait partie du modèle ; le réécrire à la main dans l'API est la source d'erreur classique) · « Comment mettre à jour scikit-learn ? » (réentraîner avec la nouvelle version, revalider, puis redéployer ; ne pas recharger l'ancien fichier) · « Et ONNX ? » (un format qui ne sert qu'à prédire, sans Python, pour un déploiement sûr et rapide).

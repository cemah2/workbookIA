### B7.Q2 — src/, tests/, configs/, scripts/ : où va quoi ?
a) **A** : une fonction importée par l'entraînement **et** par l'API appartient au paquet ; c'est la parade au training-serving skew (une seule fonction de prétraitement). b) **D** : un programme lancé à la main, une fois, qui n'est importé par personne. c) **C** : un fichier de réglages. d) **B** : pytest cherche les tests dans `tests/`. e) **Faux** : données et sorties de runs restent hors de git (`.gitignore`) ; on les retrouve par un script (b) et une empreinte (207.4). ### B7.Q3 — print ou logging : niveaux, destinations et messages utiles
a) **B** : une étape normale du run, `INFO`. b) **C** : inattendu (on attendait un GPU), mais le programme continue, dix fois plus lentement : `WARNING`, que quelqu'un doit voir. c) **2** : le niveau `WARNING` laisse passer `WARNING` et `ERROR`, et masque `DEBUG` et les trois `INFO`. d) **Faux** : un module de bibliothèque écrit par `log.info(...)` ; seul le point d'entrée configure les handlers, une fois. ### B7.Q4 — Ce qui va dans la configuration, et ce qui ne doit jamais y aller
a) **ACD** : le learning rate, la graine et un chemin relatif sont des réglages du run ; une clé d'API est un secret, qui arrive par une variable d'environnement. b) **A** : PyYAML suit YAML 1.1, dont la notation scientifique exige un point dans la mantisse ; `5e-4` reste la chaîne `'5e-4'`, et `"5.0e-4"` est une chaîne à cause des guillemets. c) **2** : `TrainConfig` refuse `epochs < 1` par une `ValueError` au chargement, que `main` attrape : `log.error(...)`, puis `return 2`, avant la moindre minute de calcul. d) **Vrai** : chaque instruction crée une couche, et l'image garde toutes ses couches ; `docker history` montre la valeur, même remplacée plus loin. e) **C** : l'historique de git garde chaque commit ; un dépôt privé se clone, se partage, peut devenir public. On révoque la clé chez le fournisseur, puis on en crée une autre. f) **Faux** : une dataclass ne vérifie pas les annotations ; c'est pourquoi la `TrainConfig` de la fiche les vérifie dans `__post_init__`.
**À retenir** : la configuration dit avec quoi on entraîne, se versionne et se valide au chargement ; un secret n'est jamais dans un fichier du dépôt ni dans une image.

### B7.Q5 — Même graine, résultats différents : les sources de non-déterminisme
a) **C** : `torch.manual_seed` fixe les générateurs de PyTorch (initialisation, dropout), pas celui de NumPy ; d'où les trois lignes de `seed_everything`. b) **Vrai** : des milliers de threads additionnent dans un ordre qui change d'un appel à l'autre, et l'addition des flottants n'est pas associative ; un écart au dernier chiffre se propage d'epoch en epoch. c) **C** : sans `warn_only`, une `RuntimeError` ; avec, un avertissement, et l'opération non déterministe s'exécute quand même. d) **Faux** : $(0{,}1 + 0{,}2) + 0{,}3 = 0{,}6000000000000001$ et $0{,}1 + (0{,}2 + 0{,}3) = 0{,}6$. e) **B** : sans `generator`, le `DataLoader` tire la graine de son mélange dans le générateur global de PyTorch au début de chaque epoch ; un tirage de plus, n'importe où avant, décale tout. D'où le `generator=g` de la fiche.
**À retenir** : une graine par générateur, un `generator` par `DataLoader`, des algorithmes déterministes, et la conscience que les flottants ne s'additionnent pas dans n'importe quel ordre.

### B7.Q6 — requirements.txt, fichier de verrouillage, pyproject.toml : qui fige quoi ?
a) **C** : une borne inférieure, ce que le code accepte au moins ; l'outil choisit la version exacte. b) **A** : `uv.lock` (écrit par `uv lock`, suivi par `uv sync`) fige chaque paquet, dépendances indirectes comprises, avec ses empreintes ; `pyproject.toml` ne donne que la borne, et le cache de pip garde des fichiers téléchargés, pas ce qu'un projet a installé. c) **Faux** : une bibliothèque garde des bornes larges ; épingler `numpy==2.1.3` la rendrait impossible à installer à côté d'une autre qui demande `numpy>=2.2`. C'est le projet qu'on **livre** qui se verrouille. d) **A** : le run a tourné avec des modifications non commitées ; le commit enregistré ne contient pas tout son code. D'où le drapeau de 207.4. e) **Vrai** : c'est le rôle d'un verrou : la même version exacte, tant qu'on ne le régénère pas. La précision « Linux, même Python » compte : un `uv.lock` est multiplateforme et peut épingler d'autres versions pour une autre plateforme ou un autre Python.
**À retenir** : `pyproject.toml` dit ce que le code supporte, le verrou ce qui a marché, et le commit propre le code exact.

### B7.Q7 — Que tester dans un projet de machine learning ?
a) **B** : les gradients s'accumulent d'un pas à l'autre, les pas deviennent trop grands ou incohérents, et la loss sur 16 images reste le plus souvent au-dessus du seuil du test (sur le CNN de la fiche, avec Adam : deux graines sur trois échouent, la troisième passe quand même) ; la forme de la sortie et le schéma des données, eux, ne voient pas la boucle du tout. Un test d'overfitting attrape ce bug souvent, pas à coup sûr. b) **C** : un test de données qui calcule l'empreinte de chaque image des deux jeux et vérifie qu'aucune n'est commune. c) **A** : l'entraînement fumée vérifie que la chaîne entière va au bout (code 0, artefact écrit), sans juger l'accuracy : 15 % sur quelques centaines d'images en une epoch ne veut rien dire. La latence de l'API est un autre test. d) **Faux** : il montre que le programme tourne, pas que le modèle apprend ; c'est le rôle du test d'overfitting d'un mini-batch et de l'évaluation. e) **1,0** : le score est le **minimum** des quatre sommes ; une équipe qui ne surveille rien a un score faible, quels que soient ses autres efforts.
**À retenir** : on teste le code et le ML : formes, données, capacité à apprendre, chaîne de bout en bout ; le maillon le plus faible fait le score.

### B7.Q8 — Artefact de modèle : les poids seuls ne suffisent pas
a) **AB** : les statistiques de normalisation déterminent ce que le modèle reçoit, et l'ordre des classes ce que veut dire sa sortie ; l'état de l'optimiseur ne sert qu'à reprendre l'entraînement, et le learning rate final décrit l'entraînement (il va dans la traçabilité du run), sans rien changer à la prédiction. b) **B** : `load_state_dict` vérifie les noms et les formes (« size mismatch for 0.weight: copying a param with shape torch.Size([12, 3, 3, 3]) … ») ; d'où l'architecture et ses arguments dans l'artefact (`{"arch": "small_cnn", "widths": [12, 24]}`), relus par le service. c) **C** : les métadonnées de safetensors n'acceptent que des chaînes (« argument 'metadata': 'int' object is not an instance of 'str' ») ; on écrit `{"version": "1"}`, et le reste dans un `meta.json`. d) **Vrai** : un seul pixel ou un seul label changé donne une autre empreinte SHA-256 ; deux empreintes égales disent que les images (et leur type, leur forme, leurs labels si on les hache) sont exactement les mêmes, dans le même ordre : les mêmes images mélangées donnent une autre empreinte. e) **C** : la version relie chaque prédiction à l'artefact qui l'a produite, donc à son run, à ses données et à sa fiche modèle ; après un retour arrière, elle montre que l'ancien artefact répond bien. Elle ne change rien au calcul ni au format d'entrée, que fixe le prétraitement de l'artefact.
**À retenir** : l'artefact, c'est les poids **plus** tout ce qui donne leur sens aux entrées et aux sorties, relu par le service, jamais recalculé.

### B7.Q9 — Latence p50, p95 et débit : ce que ressent l'utilisateur
a) **29** : $\frac{900 \times 10 + 100 \times 200}{1\,000} = 29$ ms, une durée qu'aucune requête n'a eue. b) **200** : triées, les requêtes 0 à 899 valent 10 ms et 900 à 999 valent 200 ms ; la position $0{,}95 \times 999 = 949{,}05$ tombe parmi les lentes. Une requête sur dix est lente : le p95 le voit, la moyenne le dilue. c) **Vrai** : 1 000 requêtes de 29 ms ont la même moyenne et un p95 de 29 ms. d) **9** : loi de Little, $L = 60 \times 0{,}150 = 9$ requêtes en cours. e) **160** : $64 / 0{,}4 = 160$ images par seconde. f) **A** : le groupe amortit les coûts fixes de chaque appel, même sur CPU (calcul vectorisé, plusieurs threads), donc le débit monte ; mais chaque requête attend la fin de son groupe (et parfois qu'il se remplisse).
**À retenir** : l'utilisateur vit le p95, la moyenne ment sur une queue ; le débit et la loi de Little dimensionnent le service.

### B7.Q10 — torch.export, ONNX, TorchScript : lequel choisir aujourd'hui ?
a) **B** : `torch.export` fige le graphe et les poids dans un `.pt2`, rechargé par `torch.export.load(...).module()` sans le code de la classe ; TorchScript est déprécié dans la 2.11, et un pickle de l'objet demande le code de sa classe au chargement. b) **A** : ONNX Runtime existe pour C#, C++, JavaScript et Java ; un `state_dict` ne se sert pas sans PyTorch et le code du modèle. c) **Faux** : `torch.compile` accélère un modèle à l'intérieur d'un programme Python ; il ne produit pas de fichier à servir. d) **B** : sans `dynamic_shapes`, la taille de batch de l'exemple est figée par une garde (« Guard failed: … == 8 ») ; on déclare `Dim("batch", …)`. e) **Faux** : depuis la 2.9, `torch.onnx.export` utilise `dynamo=True` par défaut, c'est-à-dire `torch.export` ; l'ancien chemin par TorchScript, le défaut de la 2.8, ne se prend plus que par `dynamo=False`. f) **A** : la condition dépend de la **valeur** de `x`, qu'un graphe figé ne connaît pas ; PyTorch 2.11 lève `GuardOnDataDependentSymNode` (« Could not guard on data-dependent expression »). On réécrit sans `if` (`torch.where`) ou avec `torch.cond`. L'option C décrit ce que faisait `torch.jit.trace`, avec un simple avertissement.
**À retenir** : `torch.export` pour figer un graphe complet, ONNX pour servir sans PyTorch, `torch.compile` pour accélérer dans Python, TorchScript pour lire l'existant.

### B7.Q11 — Écart entraînement-production et dérive des données : vrai ou faux
a) **Vrai** : le modèle est figé, le monde non (dérive des entrées, des classes, de la relation). b) **Faux** : le training-serving skew vient de deux chaînes de préparation qui diffèrent ; il existe dès le premier jour, sans que le monde change. La dérive, elle, vient du monde. c) **Vrai** : avec beaucoup de données, un test devient sensible à des écarts minuscules ; la p-valeur dit la certitude, pas la taille : on juge sur $D$ ou le PSI. d) **Vrai** : la distribution des classes prédites se compare à celle de la référence sans attendre les labels (le biais de prédiction de Sculley et coll.). e) **A** : les images reçues changent (une dérive des entrées), alors que la préparation et le lien entre une image et sa classe restent les mêmes ; un chat reste un chat, mais plus saturé. f) **Faux** : les bornes se fixent une fois, sur la référence ; recalculées sur la production, elles mesureraient chaque semaine autre chose.
**À retenir** : skew = deux préparations ; dérive = le monde ; on mesure la taille d'un écart sur des fenêtres et des bornes fixes.

### Ex B7.1 — Taille d'un artefact : float32, bfloat16, int8, et la mémoire au chargement ✏️
**Réponse** : a) **114,4** ; b) **109,1** ; c) **57,2** ; d) **28,6** ; e) **34,4** ; f) **3,3** ; g) **218,1** ; h) **293 656** ; i) **2 808** ; j) **0,9**.
**Démarche** : a) $4 \times 28\,589\,128 = 114\,356\,512$ octets, soit 114,4 Mo. b) $114\,356\,512 / 1\,048\,576 = 109{,}06$ Mio : le Mio est 4,9 % plus grand que le Mo, d'où l'écart. c) $2 \times N = 57\,178\,256$ octets. d) $N = 28\,589\,128$ octets. e) Les matrices denses passent à 1 octet : $26\,646\,528$ octets ; le reste, $28\,589\,128 - 26\,646\,528 = 1\,942\,600$ paramètres (dont les $34\,120$ biais), garde 4 octets : $7\,770\,400$ octets ; total $34\,416\,928$ octets. f) $114{,}36 / 34{,}42 = 3{,}32$ : presque le gain maximal (4), parce que 93 % des paramètres de ConvNeXt sont dans des couches denses (ses blocs font leurs « convolutions 1 × 1 » avec des `nn.Linear`). Mesuré en session : le `state_dict` quantifié écrit par `torch.save` pèse 34 507 327 octets, ≈ 90 ko de plus que le calcul (échelles, points zéro, emballage des poids, pickle). g) Deux copies de b) : 218,1 Mio. h) Buffers float32 : $2 \times (16 + 16 + 32 + 32 + 64 + 64) = 448$ valeurs ; $4 \times (72\,954 + 448) = 293\,608$ octets, plus $6 \times 8 = 48$ octets de compteurs : $293\,656$. i) $296\,464 - 293\,656 = 2\,808$ octets : l'en-tête de safetensors, 8 octets qui donnent sa longueur, puis 2 800 octets de JSON qui donnent pour chacun des 38 tenseurs (6 convolutions, 6 batchnorms de 5 tenseurs, la couche dense et son biais) son nom, son type, sa forme et sa position dans le fichier ; ici, aucune métadonnée. j) $100 \times 650 / 72\,954 = 0{,}89\,\%$. Dans ta copie : la quantification dynamique ne touche que les couches listées (`{nn.Linear}`) ; le VGG n'a que 0,9 % de ses paramètres dans sa couche dense : son fichier ne baisserait presque pas. La fiche abaisse le pic g) en construisant le modèle sur le device `meta` (aucune mémoire), puis en chargeant avec `torch.load(..., mmap=True)` et `load_state_dict(..., assign=True)` : une seule copie, lue à la demande. La taille du fichier est un plancher : il faut aussi les activations, les copies temporaires, l'interpréteur et la bibliothèque.
**Erreurs fréquentes** : compter 4 bits au lieu de 4 octets ; confondre Mo et Mio ; passer tout le modèle en int8 alors que la quantification dynamique ne touche que les matrices des couches listées ; oublier les buffers des batchnorms, ou compter `num_batches_tracked` en float32 ; croire que la mémoire au chargement vaut la taille du fichier.
**Variante** : un modèle de 50 millions de paramètres, stocké en bfloat16, doit tourner sur une machine qui lui laisse 256 Mio. Réponse : son fichier pèse 100 Mo, soit 95,4 Mio ; un chargement naïf en float32 (modèle construit en float32, puis copie lue) monte à $190{,}7 + 95{,}4 \approx 286$ Mio, au-delà de la limite ; construit directement en bfloat16, deux copies font 190,7 Mio, et avec `meta`, `mmap` et `assign`, environ 95 Mio.

### Ex B7.2 — Cinq graines, un intervalle : la dispersion d'une accuracy rapportée ✏️
**Réponse** : a) **64,4** ; b) **0,548** ; c) **0,245** ; d) **0,68** ; e) **63,72** ; f) **Vrai** ; g) **0,6** ; h) **0,35** ; i) **Faux**.
**Démarche** : a) $322{,}0 / 5 = 64{,}4$. b) Écarts $-0{,}2$ ; $0{,}6$ ; $-0{,}8$ ; $0{,}4$ ; $0$, carrés $0{,}04 + 0{,}36 + 0{,}64 + 0{,}16 + 0 = 1{,}20$ ; $s = \sqrt{1{,}20/4} = \sqrt{0{,}30} = 0{,}5477$. c) $0{,}5477 / \sqrt 5 = 0{,}2449$. d) $2{,}776 \times 0{,}2449 = 0{,}680$ (avec le quantile exact de SciPy, 2,7764, 0,6801). e) $64{,}4 - 0{,}68 = 63{,}72$, et la borne haute 65,08. f) B : moyenne 65,0, écarts $-0{,}1$ ; $0{,}3$ ; $-0{,}5$ ; $0{,}6$ ; $-0{,}3$, somme des carrés 0,80, $s = \sqrt{0{,}20} = 0{,}4472$, erreur type 0,2, demi-largeur 0,555 : [64,44 ; 65,56], qui recouvre [63,72 ; 65,08]. g) Différences 0,7 ; 0,3 ; 0,9 ; 0,8 ; 0,3, de moyenne 0,6. h) Écarts 0,1 ; −0,3 ; 0,3 ; 0,2 ; −0,3, somme des carrés 0,32, $s = \sqrt{0{,}08} = 0{,}2828$, erreur type 0,1265, demi-largeur $2{,}776 \times 0{,}1265 = 0{,}351$. i) [0,25 ; 0,95] ne contient pas 0 : B bat A sur chaque graine, de 0,3 à 0,9 point. Dans ta copie : on écrit **64,4 % ± 0,7 (intervalle à 95 % sur 5 graines)**, soit [63,7 ; 65,1]. f) et i) diffèrent parce qu'une partie de la variation vient de la **graine** et touche A et B ensemble (les graines 1 et 3 sont bonnes pour les deux) : la différence graine par graine l'annule. Deux intervalles qui se chevauchent ne prouvent pas l'égalité ; on croit i), qui répond à la question posée. Un bootstrap de cinq valeurs ne peut tirer que $\binom{9}{5} = 126$ échantillons différents à l'ordre près, et il estime la dispersion comme si $n$ était grand (sans le facteur de Student) : ses intervalles sont grossiers et trop étroits. Ne garder que la meilleure graine ferait annoncer 65,0 % pour A, 0,6 point au-dessus de sa moyenne.
**Erreurs fréquentes** : diviser par $n$ au lieu de $n - 1$ ; prendre 1,96 au lieu du quantile de Student ; lire la table à $n$ degrés de liberté ; multiplier $t$ par $s$ au lieu de l'erreur type ; conclure « pas de différence » parce que les deux intervalles se chevauchent ; comparer des modèles entraînés sur des graines différentes.

### Ex B7.5 — Fermi : servir 100 requêtes par seconde — cœurs CPU, regroupement en batches, coût mensuel 🧮

### Ex B7.7 — Journaliser les prédictions en production : minimisation, durée de conservation, droits des personnes ⚖️
**Réponse** :
1. **Les données personnelles.** L'identifiant du compte et l'adresse IP se rattachent à une personne ; la photo aussi, dès qu'elle montre un visage, un reflet, un intérieur, une adresse sur un colis, ou qu'elle est rattachée au compte, même si elle montre un objet. La classe, la probabilité, la catégorie choisie et la latence deviennent personnelles une fois rattachées au compte. Un pseudonyme calculé avec une clé secrète reste, pour la plateforme qui détient la clé, une donnée personnelle (le RGPD le dit de la pseudonymisation : art. 4, point 5, et considérant 26) : quiconque a la clé peut refaire le lien. Il réduit le risque, il ne sort pas le journal du RGPD.
2. **La minimisation.** Pour la dérive et la qualité : l'heure (arrondie à l'heure), le pseudonyme du compte, la version du modèle, des **statistiques de l'image** (luminosité moyenne, contraste, taille, éventuellement les probabilités des dix classes), la classe proposée, sa probabilité, la catégorie choisie par le vendeur (un label gratuit, qui mesure la qualité sans annotation), la latence. Ni l'adresse IP (inutile au modèle ; les journaux de sécurité ont leur propre régime), ni la photo entière : les statistiques suffisent au PSI et au test KS de 207.10.
3. **La finalité.** Réentraîner est une autre finalité que surveiller. L'article 6, paragraphe 4, demande d'en vérifier la compatibilité avec la finalité initiale (le lien entre les deux, le contexte de la collecte, la nature des données, les conséquences pour les personnes, les garanties comme la pseudonymisation) ; une photo prise chez soi n'est pas une donnée anodine. Il faut au minimum informer les vendeurs (art. 13), et plus sûrement leur proposer de contribuer à l'amélioration par un choix explicite, sur un échantillon limité, avec une base légale écrite. C'est aussi à documenter dans la fiche modèle.
4. **La conservation.** Par exemple : les lignes détaillées pseudonymisées, 90 jours (le temps de détecter une dérive et de comparer des fenêtres) ; un éventuel échantillon de photos versées volontairement, la durée annoncée aux vendeurs, au plus le temps du réentraînement et de son audit ; les statistiques agrégées par jour, sans pseudonyme, sans limite (ce ne sont plus des données personnelles si l'agrégation est assez large). On fait respecter ces durées par une purge automatique planifiée, testée, et inscrite au registre. La fourchette de la délibération 2021-122 vise la journalisation **de sécurité** des accès (qui a fait quoi, pour détecter les intrusions) : une autre finalité, qui ne justifie pas de garder des prédictions et des photos.
5. **Les droits.** Le journal doit permettre de retrouver toutes les lignes d'un vendeur : une table de correspondance compte → pseudonyme, protégée et séparée, ou la clé qui recalcule le pseudonyme à partir de l'identifiant. Pour l'accès (art. 15), on extrait ses lignes et on dit à quoi elles servent et combien de temps elles sont gardées ; pour l'effacement (art. 17), on supprime ses lignes détaillées et ses photos éventuelles, et on note que les agrégats, anonymes, restent. Un modèle déjà entraîné sur ses photos pose une question plus difficile (le réentraîner sans elles à la prochaine version) : raison de plus pour ne pas les garder par défaut.
6. **La sécurité.** Dans le code : un gestionnaire d'erreur qui répond 422 avec le message et la position de l'erreur, sans le champ `input` ; des messages de log sans le corps de la requête (un `log.exception` dans un `except` qui écrit le pseudonyme, la route et le type d'erreur, pas les pixels) ; la protection dès la conception (art. 25) comme règle de revue de code. Dans l'exploitation (art. 32) : accès aux journaux restreint et tracé, chiffrement au repos, séparation entre journaux techniques et journal des prédictions, durée courte pour les journaux techniques.
7. **Fiche modèle, « Journalisation et données ».** Journal des prédictions : heure arrondie, compte pseudonymisé, version, statistiques de l'image (luminosité, contraste), classe, probabilité, catégorie choisie, latence ; ni photo ni adresse IP. Finalités : surveillance de la dérive et de la qualité ; le réentraînement n'utilise que des photos données volontairement. Conservation : 90 jours pour les lignes, agrégats anonymes ensuite ; purge automatique quotidienne. Droits : accès et effacement par compte, sous un mois. Sécurité : accès restreint et tracé, aucune entrée dans les réponses d'erreur ni dans les journaux techniques.

**Erreurs fréquentes** : croire qu'une photo d'objet n'est jamais une donnée personnelle ; croire qu'un pseudonyme anonymise ; garder « au cas où », sans durée ; réutiliser un journal de surveillance pour entraîner sans se poser la question de la finalité ; transposer la durée des journaux de sécurité à un journal de prédictions ; oublier les journaux techniques et les réponses d'erreur, qui recopient les entrées ; prendre ce résumé pour un avis juridique (le délégué à la protection des données tranche).
**Variante** : la plateforme veut garder 1 % des photos, tirées au hasard, pour vérifier à la main la qualité du modèle chaque mois. Réponse : c'est une finalité de surveillance de la qualité, plus proche de la finalité initiale que le réentraînement, mais qui garde des photos ; on la limite (1 %, durée courte, par exemple 30 jours, visionnage par une équipe restreinte), on floute ou l'on écarte les photos où apparaissent des personnes, on informe les vendeurs, et on l'inscrit au registre et dans la fiche modèle.

### Ex B7.8 — Sculley et coll. (2015) : « Hidden Technical Debt in Machine Learning Systems » 📄
**Réponse** :
1. **La métaphore.** Ward Cunningham, en 1992 ; comme une dette financière, elle peut être raisonnable, mais elle doit être remboursée. La dette cachée est dangereuse parce qu'elle « compounds silently » : elle grossit sans qu'on la voie. L'article ne propose aucun algorithme de ML nouveau : il veut rendre visibles des compromis de long terme, au niveau du système plutôt que du code.
2. **La figure 1.** Dix boîtes : Configuration, Data Collection, Data Verification, Machine Resource Management, Feature Extraction, **ML Code** (la petite boîte noire au milieu), Analysis Tools, Process Management Tools, Serving Infrastructure, Monitoring. Le MP5 a déjà le code de ML, l'extraction des features (le prétraitement), la collecte (le téléchargement de CIFAR-10), des outils d'analyse (courbes, matrice de confusion) et un début de configuration. Le chapitre ajoute la configuration validée, la vérification des données (tests, empreintes), le service (API) et la surveillance (dérive), et un peu de gestion des processus (CI). Restent absents ou rudimentaires : la gestion des ressources de calcul et la gestion de nombreux processus.
3. **Les frontières.** CACE (*Changing Anything Changes Everything*) : changer la distribution d'une entrée, une feature, un hyperparamètre ou la sélection des données change tout le reste ; dans ton projet, changer la normalisation ou l'augmentation change les poids appris et le seuil de confiance qu'utilise l'API. Un consommateur non déclaré utilise la sortie d'un modèle (dans un fichier, des journaux, une API) sans que l'équipe le sache ; tout changement du modèle peut le casser. Parades : des restrictions d'accès et des accords de service stricts (SLA). Ton API (📦 B7.18) est exactement ce point d'accès : une version dans chaque réponse, et une liste de qui l'appelle.
4. **Les dépendances de données.** Contre une dépendance instable (un signal produit par un autre système, qui change), une copie versionnée et figée du signal, mise à jour après vérification ; le prix : un signal qui vieillit et plusieurs versions à maintenir. Une dépendance sous-utilisée s'installe par les « legacy features » (devenues redondantes), les « bundled features » (ajoutées en groupe), les « ε-features » (pour un gain minuscule) et les « correlated features » (corrélées à une feature plus causale) ; on la détecte par des évaluations régulières qui retirent une feature à la fois (*leave-one-feature-out*). L'empreinte des données (207.4) protège contre un jeu qui change sous le même nom (une dépendance instable de fait) et rend un run rejouable ; elle ne dit rien d'une feature inutile ni d'un signal amont qui dérive après l'entraînement.
5. **Les boucles.** Directe : le modèle influence le choix de ses propres données d'entraînement futures ; les auteurs notent que la solution théorique, les bandits, passe mal à l'échelle, et proposent un peu de hasard (*randomization*) ou des données isolées de l'influence du modèle. Cachée : deux systèmes s'influencent à travers le monde, comme un système qui choisit les produits d'une page et un autre qui choisit les avis affichés, ou deux modèles boursiers de deux entreprises. Pour la plateforme de ⚖️ B7.7 : les catégories proposées changent ce que les acheteurs cherchent et cliquent, donc les catégories que les vendeurs choisissent, donc les labels « gratuits » du réentraînement.
6. **Les anti-patterns.** Un système mûr peut être fait d'« au plus 5 % » de code de ML et d'« au moins 95 % » de code de colle ; parade : envelopper les paquets génériques dans des API communes, ou écrire une solution propre. Une jungle de pipelines : une préparation des données faite de collectes, de jointures et d'échantillonnages ajoutés au fil de l'eau, avec des fichiers intermédiaires, difficile à tester et à réparer. Knight Capital a perdu 465 millions de dollars en 45 minutes, apparemment à cause de chemins de code expérimentaux obsolètes (*dead experimental codepaths*). Les trois odeurs : *plain-old-data type*, *multiple-language*, *prototype*.

    images = np.asarray(images)
    if images.dtype != np.uint8:
        raise ValueError(f"preprocess expects uint8 images (0..255), got {images.dtype}")
    if images.ndim == 3:
        images = images[None]
    if images.ndim != 4 or images.shape[1:] != (32, 32, 3):
        raise ValueError(f"expected images of shape (N, 32, 32, 3) or (32, 32, 3), got {images.shape}")
    x = torch.from_numpy(np.ascontiguousarray(images)).permute(0, 3, 1, 2).to(torch.float32) / 255.0
    m = torch.tensor(mean, dtype=torch.float32).view(1, 3, 1, 1)
    s = torch.tensor(std, dtype=torch.float32).view(1, 3, 1, 1)
    return ((x - m) / s).contiguous()

### Ex B7.12 — Prédire : même graine, puis num_workers = 4, puis GPU — résultats identiques ? 🔮
**Réponse** : a) **`True`** ; b) **`True`** ; c) **`False`** (écart maximal des poids : 0,027) ; d) **`True`**. Les quatre réponses sont les mêmes pour les graines 0, 1 et 2 et pour 256 ou 512 images (`history_chB7.py`), l'écart de c) allant de 0,014 à 0,029. e) Sur un GPU, les poids ne sont en général **pas** ceux du CPU (d'autres noyaux de calcul, qui additionnent dans un autre ordre), et deux runs sur le même GPU ne sont identiques qu'avec `torch.use_deterministic_algorithms(True)` et `torch.backends.cudnn.benchmark = False` (207.4) ; la cellule le mesure sur Colab.
**Démarche** : a) un run à 0 worker est une suite d'opérations fixée par `torch.manual_seed(0)` : rejoué, il refait les mêmes tirages, dans le même ordre, sur le même processeur. b) Avec des workers, chaque processus fils sème son générateur avec une graine de base que le `DataLoader` tire, à chaque epoch, dans **son** `generator` (graine 0), plus le numéro du worker : rejoué, chaque worker refait les mêmes retournements. c) À 0 worker, les retournements sont tirés dans le générateur global du notebook, juste après l'initialisation des poids ; à 4 workers, dans les générateurs des workers : ce ne sont pas les mêmes tirages, donc pas les mêmes images retournées, donc pas les mêmes poids. d) Sans retournement, plus rien n'est tiré dans `__getitem__` : l'ordre des mini-batches vient du `generator`, le même dans les deux cas, et les workers ne font que lire les images. La leçon : `num_workers` fait partie de la configuration d'un run reproductible dès qu'une augmentation tire au hasard ; `worker_init_fn` sème aussi NumPy et `random` dans chaque worker (sinon des workers créés par `fork` peuvent copier le même état NumPy), mais ne rend pas un run à 4 workers égal à un run à 0 worker.
**Erreurs fréquentes** : croire que `num_workers` ne change que la vitesse ; croire qu'un run à 4 workers ne se rejoue pas (il se rejoue, avec le même `generator`) ; oublier que le GPU change les nombres même à graine fixée.
**Variante** : avec `persistent_workers=True`, les workers sont créés une seule fois, et leurs générateurs continuent d'une epoch à l'autre au lieu d'être semés de nouveau : un run reste rejouable avec les mêmes réglages, mais ses retournements de la deuxième epoch diffèrent de ceux d'un run sans workers persistants.

### Ex B7.17 — L'artefact du modèle : safetensors, configuration, normalisation, classes, version, empreinte des données 📦
**Réponse** : `solutions/b7_cifarprod/src/cifarprod/artifact.py`, et dans `cli.py` l'appel `save_artifact(out, ...)` qui remplace l'écriture des seuls poids ; les neuf vérifications passent. L'artefact du VGG du MP5 tient en deux fichiers : `model.safetensors` (296 504 octets : les 38 tenseurs du `state_dict`, buffers des batchnorms compris, et un en-tête qui porte maintenant `package_version`) et `meta.json` (872 octets). **Démarche** :
```python
def save_artifact(folder, model, *, arch, widths, mean, std, classes, data, metrics=None) -> Path:
    folder = Path(folder)
    folder.mkdir(parents=True, exist_ok=True)
    state = {k: v.detach().cpu().contiguous() for k, v in model.state_dict().items()}
    save_file(state, str(folder / WEIGHTS), metadata={"package_version": __version__})
    meta = {"package_version": __version__, "created": datetime.now(timezone.utc).isoformat(timespec="seconds"),
            "arch": str(arch), "widths": [int(w) for w in widths], "input": dict(INPUT),
            "mean": [float(m) for m in mean], "std": [float(s) for s in std], "classes": [str(c) for c in classes],
            "data": dict(data), "metrics": dict(metrics or {}), "torch": torch.__version__,
            "python": platform.python_version(), "weights_sha256": file_sha256(folder / WEIGHTS)}
    (folder / META).write_text(json.dumps(meta, indent=1, sort_keys=True) + "\n", encoding="utf-8")
    return folder
```
L'artefact répond aux trois questions qu'un service se pose : **comment reconstruire** le modèle (`arch`, `widths`, les poids), **comment préparer** une image (`input`, `mean`, `std` appris sur l'entraînement), **comment nommer** une sortie (`classes`, dans l'ordre des sorties). Il répond aussi à celles de la personne qui le relit six mois plus tard : quel code (`package_version`), quelles bibliothèques (`torch`, `python`), quelles données (`data`, l'empreinte des images **et** des labels, celle du journal de B7.14), quels poids (`weights_sha256`). `load_artifact` vérifie cette dernière avant de charger : un fichier de poids remplacé à la main, ou corrompu, est refusé au lieu de servir en silence un autre modèle. `predict_images` passe par `preprocess`, la fonction de l'entraînement : il n'y a plus deux chaînes de préparation, donc plus de training-serving skew possible sur ce point. Des cinq écarts de B7.16, l'artefact en supprime trois (la normalisation recalculée, l'ordre des classes, `eval()` oublié, désormais dans `load_artifact`) ; la lecture d'une image en BGR et le float64 restent possibles dans le code qui lit le fichier envoyé, d'où l'API de B7.18, qui reçoit des pixels RGB déjà décodés, et le test de non-régression. La fiche modèle du ch. 23 (ou de 🛠️ B6.28) va à côté de ce dossier, dans le dépôt (`MODEL_CARD.md`), et cite son `weights_sha256`.

### Ex B7.18 — Une API de prédiction avec FastAPI (repli : http.server) : /health, /predict, validation des entrées 📦
**Réponse** : `solutions/b7_cifarprod/src/cifarprod/serve.py` ; les seize vérifications passent, et les deux serveurs donnent les mêmes réponses : les noms du notebook sur 8 images et un batch de 32, 422 sans l'entrée pour les huit requêtes mal formées, 500 `{"detail": "internal error"}` pour un modèle qui plante, et un serveur arrêté, port libéré, même après une erreur dans le bloc de `running`.
**Démarche** :
```python

    async def invalid(request: Request, exc: RequestValidationError):
        return JSONResponse(status_code=422, content={"detail": errors_without_input(exc.errors())})

    @app.post("/predict")
    def predict(image: Image):
        try:
            answer = app.state.service.predict([image.pixels])[0]
        except Exception:                                  # noqa: BLE001 - logged, a clean 500 for the client
            log.exception("prediction failed")
            return JSONResponse(status_code=500, content={"detail": "internal error"})
        return {**answer, "model_version": app.state.service.version}
```
Le service sépare trois rôles. **Valider** : `Image` et `Batch` refusent avant tout calcul ce qui n'est pas une image 32 × 32 × 3 d'entiers de 0 à 255 ; le modèle n'a pas à se méfier de ses entrées, et la même définition sert aux deux serveurs. **Prédire** : `Service` charge l'artefact une seule fois et ne connaît pas HTTP. **Transporter** : FastAPI d'un côté, `BaseHTTPRequestHandler` de l'autre, qui ne font que lire, appeler `Service` et répondre. Par défaut, FastAPI renvoie dans un 422 l'entrée refusée : pour une image de 28 × 28, une réponse de 6 481 octets qui contient tous les pixels envoyés ; avec le gestionnaire ci-dessus, 124 octets, le message et l'emplacement seulement (⚖️ B7.7 : une image envoyée peut montrer une personne). Une erreur interne donne un 500 sans trace (la trace va dans le journal du serveur, pas au client, qui n'a pas à connaître ton code). `running` porte la leçon de la fiche : tout ce qui démarre un serveur l'arrête dans un `finally` ; sinon, la cellule réexécutée trouve son port déjà pris et le thread de l'ancien serveur tourne encore. `protocol_version = "HTTP/1.1"` garde la connexion ouverte d'une requête à l'autre ; `disable_nagle_algorithm` évite qu'en-têtes et corps, écrits séparément, attendent 40 ms l'accusé de réception du client (mesuré : 48 ms par requête sans lui, 6 ms avec).
**Erreurs fréquentes** : le 422 par défaut de FastAPI (l'entrée renvoyée telle quelle) ; une exception du modèle non rattrapée (le client reçoit `Internal Server Error` en texte, pas en JSON, et aucune ligne de log ne dit pourquoi) ; `Batch` sans bornes (65 images acceptées, un batch vide qui plante dans `preprocess` : 500 au lieu de 422) ; `server.shutdown()` après le `yield` mais hors d'un `finally` (une erreur dans le bloc laisse le port ouvert) ; le modèle rechargé à chaque requête (dix fois plus lent) ; `main` qui rend 0 quand l'artefact manque (un orchestrateur croit le service démarré) ; une réponse HTTP/1.1 sans `Content-Length` (le client attend la fin d'une réponse qui ne vient pas).

| Batch | float32, 2 threads | no_grad | autograd actif | 1 thread | bfloat16 | int8 dynamique |
|---|---|---|---|---|---|---|
| 1 | 1,8 | 2,5 | 2,6 | **0,9** | 3,4 | 2,1 |
| 32 | 16,9 | | | 18,3 | 21,1 | 17,6 |

Sur 1 000 images de test : accuracy 0,848 en float32 et en bfloat16, 0,846 en int8 dynamique ; accord des décisions avec le float32 : 99,5 % (5 images sur 1 000) et 99,8 % (2 images), écarts maximaux des logits 0,10 et 0,09.
**Démarche** :
```python
def bfloat16_20(model):
    low = copy.deepcopy(model).to(torch.bfloat16)
    return lambda x: low(x.to(torch.bfloat16)).float()
```
**Le batch** est le seul levier qui multiplie le débit (≈ 550 images par seconde à batch 1, ≈ 1 900 à batch 32). **Les threads** : pour une image, deux threads sont plus lents qu'un seul (0,9 contre 1,8 ms) : le travail est trop petit pour être partagé, et réveiller un second thread coûte plus qu'il ne rapporte ; à batch 32, le second thread gagne un peu. **L'autograd** : `inference_mode` gagne 0,2 à 0,8 ms par appel (selon l'exécution) sur `no_grad` et l'autograd actif, parce qu'il ne garde rien pour une passe arrière ; sur un gros modèle, c'est surtout de la mémoire gagnée. **Le bfloat16 ralentit** : ce processeur n'a pas d'instructions de calcul en 16 bits pour ces convolutions, PyTorch convertit et reconvertit ; sur un processeur qui en a (AMX des Xeon récents) ou un GPU, ce serait l'inverse. **La quantification dynamique ne change presque rien** : elle ne touche que la couche dense, 0,9 % des paramètres du VGG (✏️ B7.1 j) ; les convolutions, qui font tout le calcul, restent en float32. Les décisions changent à peine (5 et 2 images sur 1 000), mais elles changent : on vérifie l'accord sur des données réelles avant de livrer. Pour un service qui reçoit une image à la fois : un thread par processus, `inference_mode`, et plusieurs processus ; pour des prédictions par batches de nuit : de grands batches et tous les threads.
**Erreurs fréquentes** : mesurer les premiers appels (le premier appel en bfloat16 ou int8 coûte plusieurs fois les suivants) ; `model.to(torch.bfloat16)` sans copie (le modèle d'origine passe en bfloat16 et tout ce qui suit change) ; `quantize_dynamic(..., inplace=True)` sur le modèle reçu ; conclure d'une seule exécution sur des écarts de 10 % (deux exécutions de la même ligne en diffèrent souvent autant) ; juger la quantification à la taille du fichier sans mesurer la vitesse ni les décisions.
**Variante** : `torch.autocast("cpu", dtype=torch.bfloat16)` au lieu de convertir le modèle ne passe en 16 bits que les opérations qui le supportent : sur les mêmes 1 000 images, 99,5 % des décisions identiques, écart maximal des logits 0,081, accuracy 0,851 ; sur ce CPU, il ne va pas plus vite que le float32.

### Ex B7.21 — Exporter avec torch.export et vérifier l'équivalence numérique (ONNX en option) 📦
**Réponse** : `solutions/b7_cifarprod/src/cifarprod/export.py` ; `wb.check` : **`True`**. L'export du VGG pèse 386 213 octets (contre 296 504 pour les poids seuls) ; rechargé dans un processus qui ne peut pas importer `cifarprod`, il donne **exactement** les logits du modèle (écart 0,0) pour des batches de 1, 7 et 64 images, et ses gardes refusent un batch de 1 025 images et une image de 28 × 28 (« Guard failed: input.size()[2] == 32 »).
**Démarche** :
```python
def export_model(model, path, max_batch: int = 1024) -> Path:
    model.eval()
    batch = torch.export.Dim("batch", min=1, max=int(max_batch))
    program = torch.export.export(model, (torch.zeros(2, 3, 32, 32),), dynamic_shapes={"input": {0: batch}})
    torch.export.save(program, str(path))
    return Path(path)
```
L'écart est nul parce que l'export ne recalcule rien autrement : il enregistre les mêmes opérations ATen, avec les mêmes poids, que le modèle appelle lui-même ; à taille de batch égale, les noyaux de calcul sont les mêmes. (Comparés à des tailles de batch **différentes**, le modèle sur 64 images et l'export sur 1, les nombres diffèrent de l'ordre de $10^{-6}$ : un autre batch choisit parfois un autre ordre de calcul.) Le `.pt2` contient le graphe en plus des poids, d'où ses 90 Ko de plus. Le mode compte : exporté en mode entraînement, ce VGG garde des batchnorms qui normalisent par les statistiques de chaque batch, et l'écart avec le modèle en `eval()` monte à 2,9 ; d'où `model.eval()` au début d'`export_model`, même si l'appelant l'a oublié. L'exemple a 2 images : `torch.export` traite à part une dimension de taille 1 (il la fige), et la dimension de batch ne serait plus libre. On choisirait ONNX quand le service ne doit pas dépendre de PyTorch du tout (ONNX Runtime en C++, sur un téléphone, dans un navigateur) ; `torch.export` suffit quand le service a PyTorch mais pas ton code.
**Erreurs fréquentes** : l'export sans `dynamic_shapes` (la taille du batch d'exemple est figée : le batch de 1 échoue, « Guard failed: input.size()[0] == 2 ») ; un exemple d'une seule image (la dimension de batch devient une constante) ; l'export en mode entraînement ; comparer le modèle et l'export sur des batches de tailles différentes, puis s'étonner d'un écart de $10^{-6}$ ; vérifier l'équivalence sur les données qui ont servi d'exemple (rien ne dit alors que le graphe généralise) ; recharger le `.pt2` dans le même processus que le modèle (on ne prouve pas qu'il se passe de ton code).
**Variante** : sans `dynamic_shapes`, l'export (batch figé à 2) pèse 384 276 octets, et refuse 1 image comme 7 : un service qui reçoit une image à la fois tomberait à la première requête ; c'est pourquoi la vérification essaie trois tailles de batch.

### Ex B7.22 — Surveiller la dérive : PSI et test KS sur des images assombries ou bruitées, quand alerter ? 📈
**Réponse** : a) **`"B"`** ; b) **`"BD"`** ; c) **`"C"`** ; d) **`"C"`** ; e) **0,16**. Le tableau (500 images par fenêtre, référence : accuracy 0,864) :

| Fenêtre | PSI lum. | KS D | KS p | PSI classes | confiance | accuracy |
|---|---|---|---|---|---|---|
| A (telles quelles) | 0,043 | 0,056 | 0,41 | 0,030 | 0,793 | 0,832 |
| B (× 0,6) | 3,745 | 0,684 | $8 \times 10^{-112}$ | 0,033 | 0,740 | 0,802 |
| C (bruit, σ = 25) | 0,054 | 0,062 | 0,29 | 1,340 | 0,525 | 0,356 |
| D (× 0,9) | 0,156 | 0,170 | $10^{-6}$ | 0,026 | 0,790 | 0,832 |

**Démarche** :
```python
def psi_22(ref, prod, bins=10, eps=1e-4):
    cuts = np.quantile(ref, np.arange(1, bins) / bins)
    q = np.bincount(np.searchsorted(cuts, ref, side="right"), minlength=bins) / len(ref) + eps
    p = np.bincount(np.searchsorted(cuts, prod, side="right"), minlength=bins) / len(prod) + eps
    return float(np.sum((p - q) * np.log(p / q)))
```
Chaque fenêtre raconte une autre histoire. **A** : d'autres images de la même source ; PSI 0,04, KS non significatif, rien à signaler : c'est le bruit d'échantillonnage d'un PSI sur 500 images, qu'il faut connaître avant de fixer un seuil. **B** : les entrées changent énormément (PSI 3,7), mais les classes prédites presque pas, et l'accuracy perd 3 points : la normalisation par canal et les convolutions rendent ce VGG peu sensible à un éclairage uniforme. Alerte sur les entrées, oui, mais pour **vérifier la chaîne d'acquisition** (une caméra mal réglée ?), pas pour réentraîner. **C** : la luminosité moyenne ne bouge pas (le bruit est centré), donc ni le PSI ni le KS des entrées ne voient rien ; mais les classes prédites changent complètement (PSI 1,34), la confiance chute, et l'accuracy tombe à 0,36 : c'est la fenêtre qui **nuit**, et seule la surveillance des **sorties** la voit. Il faut alerter, revenir en arrière ou bloquer la source, puis réentraîner avec du bruit. **D** : un « petit changement » au sens de Lewis (PSI 0,16), sans effet sur les sorties ni sur l'accuracy ; le KS le déclare pourtant très significatif ($p = 10^{-6}$) : avec 500 images, un décalage de la luminosité de 10 % se détecte sans peine, et avec 50 000 images par fenêtre, la p-valeur serait encore bien plus petite pour le même écart. Une p-valeur mesure la **certitude** d'un écart, pas sa **gravité** (207.10) : on surveille D de plus près, on n'agit pas. La leçon de Rabanser et coll. se lit ici : surveiller les sorties du modèle (classes prédites, confiance) attrape ce qui nuit, quelle que soit la variable d'entrée qui a changé.
**Erreurs fréquentes** : une valeur égale à une coupure envoyée en dessous (`searchsorted` par défaut, `side="left"`) ; $\varepsilon$ ajouté aux seules parts de la production (une part nulle de la référence donne un PSI infini) ; des coupures recalculées sur la production ; les quartiles de ✏️ B7.4 au lieu des déciles ; `np.bincount` sans `minlength` (une classe absente décale tout) ; alerter sur toute p-valeur sous 0,05 (D) ; conclure de B qu'une grosse dérive des entrées nuit forcément ; ne surveiller que les entrées (C passe).
**Variante** : avec les deux moitiés du test échangées (la référence devient la production), le PSI de la luminosité de D vaut 0,246, tout près du seuil de 0,25, au lieu de 0,156 : un PSI dépend de l'échantillon, et un seuil appliqué à une seule fenêtre de 500 images bascule pour presque rien. Les autres réponses ne changent pas (B 4,3 ; C sous 0,04 ; classes prédites de C : 1,39).

### Ex B7.24 — Lire et compléter un Dockerfile : image de base, dépendances CPU, utilisateur non root, variables 📦
**Réponse** : `solutions/b7_cifarprod/Dockerfile`, `.dockerignore` et `requirements-serve.txt` ; les quinze points de la relecture passent. Le Dockerfile du collègue en manquait onze.
**Démarche** :
```dockerfile
FROM python:3.13.18-slim-trixie
ENV PYTHONUNBUFFERED=1 \
    PYTHONDONTWRITEBYTECODE=1 \
    PIP_NO_CACHE_DIR=1 \
    MODEL_DIR=/app/artifact
WORKDIR /app
COPY requirements-serve.txt .
RUN pip install torch==2.11.0 --index-url https://download.pytorch.org/whl/cpu \
    && pip install -r requirements-serve.txt
COPY pyproject.toml .
COPY src/ src/
RUN pip install --no-deps .
COPY artifact/ artifact/
RUN groupadd --system app && useradd --system --no-log-init --gid app app
USER app
EXPOSE 8000
CMD ["python", "-m", "cifarprod.serve", "--host", "0.0.0.0", "--port", "8000"]
```
Les lignes du collègue, et ce qu'elles auraient fait. `FROM python:latest` : une image qui change sous tes pieds (aujourd'hui Python 3.14, pas la 3.13 de ton code), et pas slim (plusieurs centaines de mégaoctets de plus). `ENV HF_TOKEN=...` : la clé reste lisible par quiconque a l'image (`docker history`) ; il faut la **révoquer** (elle a été écrite dans un fichier, peut-être commitée) et la passer au lancement (`docker run -e HF_TOKEN`, ou le gestionnaire de secrets de la plateforme). `COPY . .` en tête : chaque modification d'une ligne de code invalide la couche, et tout se réinstalle (plusieurs minutes) ; il copie aussi les données, `.git` et un éventuel `.env` si le `.dockerignore` ne les exclut pas. `pip install torch` sans index : la version CUDA, plusieurs gigaoctets, inutiles sur CPU. Pas de `USER` : le serveur tourne en root dans le conteneur. `CMD python -m cifarprod.serve` en forme shell : le processus principal est `/bin/sh`, qui ne transmet pas le signal d'arrêt de `docker stop` (le serveur est tué après 10 s au lieu de s'arrêter proprement), et sans `--host 0.0.0.0`, le serveur n'écoute que l'intérieur du conteneur. Sur ton PC, `127.0.0.1` est au contraire le bon choix : il n'expose pas ton API au réseau local.
**Erreurs fréquentes** : `python:3.13-slim` (un tag qui bouge à chaque version corrective) ; `USER app` avant les `pip install` (l'utilisateur n'a pas le droit d'installer) ou avant `useradd` ; `ENV MODEL_DIR` qui ne désigne pas le dossier copié ; `requirements-serve.txt` sans versions, ou avec `torch` (pip le prendrait sur PyPI) ; `EXPOSE 8000` et `--port 8080` ; un `.dockerignore` oublié (le contexte de build envoie `data/` et ses mégaoctets à chaque build).
**Variante** : `CMD ["uvicorn", "--factory", "cifarprod.serve:app_from_env", "--host", "0.0.0.0", "--port", "8000"]` lance uvicorn directement, l'artefact lu dans `MODEL_DIR` : la relecture passe aussi les quinze points ; avec plusieurs processus (`--workers 2`), chacun charge son propre modèle (≈ 0,3 Mo ici, plusieurs gigaoctets pour un grand modèle : la mémoire limite le nombre de processus).
